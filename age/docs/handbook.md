# Руководство по контенту

Этот документ — для человека, который сядет и будет делать арт для Age: тайлы,
пропсы, персонажей, декор, наполнение мира. Он объясняет, как устроен конвейер,
как в него добавлять своё, и какие ошибки здесь уже были совершены и записаны,
чтобы их не совершать заново.

Остальные документы отвечают на другие вопросы: [architecture.md](architecture.md) —
про слои и цикл тиков, [protocol.md](protocol.md) — про байты на сокете,
[worldgen.md](worldgen.md) — про генерацию рельефа, [art-pipeline.md](art-pipeline.md) —
краткий обзор конвейера арта. Здесь — практика.

Что есть на сегодня, в цифрах: 23 тайла, 12 ground-рецептов, 23 prop-рецепта (из
них 12 — декор без своего тайла), 78 кадров в атласе, 26 цветовых рамп, один
процедурный персонаж на 30 кадров, два импортёра. Этого хватает, чтобы мир не
был серым и чтобы площадь хаба выглядела обжитой, и не хватает ни для чего
большего: за пределами хаба мир — это одно дерево, один куст и один камень,
размноженные разбросом. Раздел [12](#12-что-делать-дальше) — честный список
того, чего не хватает.

## 0. Рабочее место

Всё, что нужно для работы над артом, работает без базы данных и почти всё —
без сервера.

```bash
# Печать всех рецептов в PNG на диск. Основной инструмент.
python scripts/probe_atelier.py [outdir]

# Кадры персонажа в 10x, чтобы судить отдельные пиксели.
python scripts/probe_character.py [outdir]
```

По умолчанию оба пишут в `.pytest-tmp/atelier`. `probe_atelier.py` кладёт туда:

| Файл | Что внутри |
| --- | --- |
| `ground.png` | контрольный лист всех ground-рецептов на шахматном фоне |
| `props.png`, `props-big.png` | то же для пропсов, второй в масштабе 3x |
| `tile-<name>.png` | каждый ground-тайл, повторённый 4×4 — здесь виден шов |
| `atlas.png`, `atlas-normal.png` | упакованные страницы, как их получает игра |
| `atlas.json` | индекс: размещения кадров |
| `character-walk.png` | ходьба во всех направлениях, 4x |
| `character-looks.png` | восемь разных внешностей, 4x |

`probe_character.py` пишет туда же четыре файла в масштабе 10×, на которых видно
отдельные пиксели: `big-facings.png` (три направления в покое),
`big-walk-down.png`, `big-walk-side.png` и `big-attack.png`.

Шахматный фон в контрольных листах — не украшение: у большинства пропсов по
краям полупрозрачные пиксели, и на плоском фоне гало не видно, а на шахматке
видно сразу.

Браузерный редактор — `/age/atelier` (см. раздел [10](#10-браузерный-редактор)).
Ему нужен собранный клиент и запущенный сервер:

```bash
cd age && npm install && npm run build
cd .. && python -m age.main --port 8140
# http://127.0.0.1:8140/age/atelier
```

Тесты, которые стоит держать зелёными при работе над артом:

```bash
python -m pytest tests/test_age_atelier.py    # 45 тестов: операции, рецепты, нормали, упаковка, привязки
python -m pytest tests -k age                 # всё вместе
cd age && npm test                            # клиент
```

## 1. Как устроен арт-пайплайн

### 1.1 Путь от рецепта до пикселя на экране

1. **Рецепт** — `Recipe` в `age/atelier/recipes.py`: ключ, размер, число кадров,
   признак бесшовности, смещение якоря и список шагов. Шаг — обычный `dict`, то
   есть JSON.
2. **Печать.** `recipes.bake(recipe, seed=..., frame=...)` создаёт `Canvas` и
   прогоняет шаги по порядку через `_apply`. Каждый шаг получает свой сид
   (`seed ^ (index * 0x9E37)`) и фазу кадра.
3. **Холст.** `Canvas` несёт три канала: `colour` (RGBA), `depth` (0–255) и
   `material` (индекс). Рисуют только в `colour`; `depth` — это рельеф,
   `material` — задел под автотайлер и звуки шагов.
4. **Упаковка.** `sheet.bake_terrain_atlas()` печатает каждый кадр каждого
   рецепта и раскладывает их полочным упаковщиком на страницу 1024×1024 с
   отступом 2 пикселя между кадрами.
5. **Нормали.** `Atlas.normal_map()` дифференцирует канал `depth` **уже
   упакованной страницы** оператором Собеля. Именно уже упакованной: отступы
   между кадрами дают бордюр, и вторую упаковку делать не надо.
6. **Экспорт.** `sheet.export()` кодирует две страницы PNG одинакового размера и
   индекс JSON. HTTP отдаёт их как `/api/atelier/atlas.png`,
   `/api/atelier/atlas-normal.png` и `/api/atelier/atlas.json`.
7. **Загрузка в браузере.** `Atlas.load(api)` в `age/frontend/src/render/atlas.ts`
   тянет все три и нарезает страницы на текстуры. Индекс несёт не только
   размещения, но и привязки тайлов к арту, список анимированных тайлов, список
   декора и раскладку листа персонажа. Это сделано специально: раньше привязки
   дублировались в TypeScript и молча разъезжались — новый тайл рисовался водой,
   и нигде не было ошибки.
8. **Рисование.** `TileLayer` (`render/tilemap.ts`) собирает каждый чанк в один
   меш с готовыми UV. `PropLayer` (`render/props.ts`) складывает всё стоячее —
   деревья, стены, декор, персонажей — в один список и сортирует по нижней
   строке, чтобы дерево внизу экрана было впереди игрока сверху.
9. **Свет.** Сцена рисуется дважды в закадровые буферы: раз цветом, раз
   нормалями. Потом полноэкранный квад (`render/lighting.ts`) читает оба и
   освещает каждый пиксель окружающим светом плюс до 24 точечных источников.
   Отсюда и нужен канал `depth`: без нормалей фонарь — это радиальный градиент
   поверх картинки.

Всё детерминировано от сида: две печати одного рецепта совпадают побайтно. На
этом держится кеширование по URL.

### 1.2 Три канала холста

| Канал | Что значит | Кто читает |
| --- | --- | --- |
| `colour` | RGBA, то, что видно | всё |
| `depth` | 0–255, насколько поверхность выступает из земли | `normals.to_normal_map` |
| `material` | индекс материала | **никто пока** |

`material` уже записывается ground-рецептами (1 — земля, 2 — трава, 3 — песок,
4 — гравий, 5 — грунтовая дорога, 6 — камень и брусчатка, 7 — доски, 8 — снег,
9 — пепел, 10 — вода), но ни одна строка кода его не читает. Это задел под
автотайлинг и звуки шагов, и это самый дешёвый визуальный выигрыш из всех
оставшихся (раздел 12).

### 1.3 Где что кешируется

Кешей четыре, и знать про них надо, потому что правка рецепта, которая «не
подействовала», почти всегда упирается в один из них.

- **Атлас в процессе Python.** `_atlas_cache` в
  `age/presentation/http_routes.py` печёт атлас один раз за жизнь процесса.
  Правка `recipes.py` или `palette.py` требует **перезапуска сервера**.
- **HTTP-кеш.** `atlas.png`, `atlas-normal.png` и листы персонажей отдаются с
  `Cache-Control: public, max-age=3600`. Час — специально: сессия не
  перезапрашивает арт, а автор, который правит рецепт, не воюет с кешем слишком
  долго. Но после перезапуска сервера браузеру нужен hard-reload.
- **Превью в редакторе не кешируется.** `POST /api/atelier/bake` отдаётся с
  `Cache-Control: no-store`, и печёт ровно тот JSON, который прислали. Поэтому
  правки в редакторе видны сразу и перезапуск для них не нужен.
- **Клиентские кеши.** `CharacterCache` держит листы персонажей по внешности,
  `DecorCache` — размещения декора по чанку (сбрасывается целиком после 512
  записей), `TileLayer` — пул мешей чанков (до 48).

### 1.4 Что делать после какой правки

| Изменили | Что нужно |
| --- | --- |
| шаги рецепта, размер, `frames` в `recipes.py` | перезапустить Python-процесс, затем hard-reload браузера |
| `palette.py` | то же (перекрасится всё, что использует рампу) |
| `character.py` | перезапуск; при той же внешности URL листа не меняется, так что нужен hard-reload |
| `TILE_GROUND`, `TILE_PROP`, `TILE_ANIMATION`, `DECOR_RECIPES` | перезапуск: клиент читает их из `atlas.json` |
| `age/domain/tiles.py` | перезапуск; плюс зеркало в `tiles.ts` и пересборка клиента |
| разброс тайлов по биомам (`BIOME_PROFILES`) | `python -m age.tools.make_fixtures`, иначе тест паритета упадёт |
| что-либо в `age/frontend/src/**` | `npm run build`, либо `npm run dev` с HMR и проксированием на порт 8140 |
| только смотрите арт, без игры | ничего: `python scripts/probe_atelier.py` |

## 2. Как добавить новый тайл

Полный пример: добавим `RUINED_WALL` — обвалившуюся каменную кладку, которая
блокирует движение и обзор, стоит в пепельных землях и при добыче даёт камень.

### 2.1 Сначала одно решение: проходимый или блокирующий

Порядок значений в `Tile` — не косметика:

```python
FIRST_BLOCKING_TILE = Tile.WATER   # 13


def is_walkable(tile: int) -> bool:
    return tile < FIRST_BLOCKING_TILE


def blocks_sight(tile: int) -> bool:
    return tile >= Tile.TREE        # 15
```

Проходимость — одно сравнение на горячем пути, поэтому все проходимые тайлы
идут до `WATER`, а все блокирующие — после. Отсюда практическое следствие:

- **Блокирующий тайл дописывается в конец** (`RUINED_WALL = 23`) — ничего не
  сдвигается, ничего не ломается. Обзор он перекроет автоматически, потому что
  23 ≥ `Tile.TREE`.
- **Проходимый тайл приходится вставлять перед `WATER`**, и это перенумерует
  все блокирующие тайлы. А идентификаторы тайлов лежат в сохранённых наложениях
  в MongoDB, в замороженных фикстурах паритета и в IntGrid-уровнях LDtk. Каждый
  сохранённый лес станет каменной стеной. Если проходимый тайл действительно
  нужен, добавляйте его тоже в конец и меняйте `is_walkable` на явную проверку
  членства — но это правка правил домена, а не контента, и её надо делать
  сознательно.

Здесь берём блокирующий, чтобы пример был честным и коротким.

### 2.2 Шаг 1 — перечисление на стороне Python

`age/domain/tiles.py`:

```python
    WALL_STONE = 20
    FENCE = 21
    CACTUS = 22
    RUINED_WALL = 23
```

### 2.3 Шаг 2 — то же на стороне TypeScript

`age/frontend/src/domain/tiles.ts`. Это обязательный шаг, и — важно — **его
никто не проверит тестом**. Паритетный тест
(`tests/test_age_client_parity.py`) читает `frontend/src/domain/constants.ts` и
сравнивает числа с `domain/constants.py`, но перечисления тайлов он не сверяет.
Расхождение здесь всплывёт как неправильная проходимость на клиенте: игрок
предскажет шаг сквозь стену, сервер его отбросит, и получится резиновый шаг на
ровном месте.

```typescript
  WALL_STONE: 20,
  FENCE: 21,
  CACTUS: 22,
  RUINED_WALL: 23,
} as const
```

### 2.4 Шаг 3 — правила домена

Что тайл делает, а не как выглядит. В `age/domain/tiles.py`:

```python
HARVEST_RESULTS: dict[int, tuple[int, str, int]] = {
    ...
    Tile.CACTUS: (Tile.SAND, "fibre", 2),
    Tile.RUINED_WALL: (Tile.BARE_GROUND, "stone", 4),
}
```

Чего мы **не** делаем и почему:

- не добавляем в `REGROWTH_LADDER` — разрушенная стена не отрастает;
- не добавляем в `PLAYER_PLACED_TILES` — иначе игрок сможет её снести
  инструментом строительства и пройти напрямик, ровно как с `CLIFF`;
- не добавляем в `BUILD_RECIPES` — материал `stone` уже занят `WALL_STONE`, и
  одному материалу соответствует один результат.

Чтобы тайл появился в мире, его надо положить в разброс биома. `scatter` —
список пар `(тайл, накопленная вероятность)`, сравниваемый по одному хешу, так
что числа должны возрастать:

```python
    Biome.ASHLAND: BiomeProfile(
        biome=Biome.ASHLAND,
        name="ashland",
        ground=Tile.ASH,
        scatter=((Tile.ROCK, 0.18), (Tile.DEAD_TREE, 0.28), (Tile.CLIFF, 0.33), (Tile.RUINED_WALL, 0.36)),
        ...
```

То же самое зеркалим в `tiles.ts`. Это меняет генерируемый рельеф, а значит —
фикстуры паритета (шаг 7).

### 2.5 Шаг 4 — ground-рецепт

У каждого тайла есть ground: бесшовный ковёр 32×32. У объектов — стен, деревьев,
камней — ground это то, на чём объект стоит, поэтому свой ковёр им обычно не
нужен. `WALL_WOOD` и `WALL_STONE` стоят на `bare_ground`; развалины поступят так
же, и шаг 4 сводится к одной строке в шаге 6.

Если бы нужен был свой ковёр, он писался бы через `_ground`, и правило тут одно:
**первым шагом всегда сплошная заливка**, чтобы ни один пиксель не остался
прозрачным. Прозрачный пиксель в ground-тайле — это дырка в полу, через которую
видно фон, и тест `test_ground_tiles_fill_their_cell_completely` падает именно
на этом.

```python
        _ground(
            "cracked_ash",
            {"op": "fill", "ramp": "dark_stone", "level": 2, "material": 9},
            {"op": "scatter", "ramp": "dark_stone", "seed": 17, "density": 0.18, "level": 1},
            {"op": "scatter", "ramp": "ember", "seed": 18, "density": 0.02, "level": 3, "depth": 6},
        ),
```

### 2.6 Шаг 5 — prop-рецепт

Проп выше тайла, привязан к его нижней кромке и рисуется на слое над рельефом.
Ширина обязана быть ровно 32 (`test_props_fit_one_cell_across`), высота —
свободна, `anchor_y` должен лежать внутри спрайта
(`test_a_prop_anchor_lies_inside_its_sprite`).

В `PROP_RECIPES`:

```python
        _prop(
            "ruined_wall",
            40,
            # Три секции кладки разной высоты. Ровная стена с ровным верхом читается как
            # крепость; развалины узнаются по обрыву. Верхний край набран отдельными
            # прямоугольниками, потому что в языке рецептов нет ластика: силуэт можно
            # только не нарисовать, а не стереть.
            {"op": "fill", "ramp": "stone", "level": 2, "depth": 236, "rect": [3, 22, 11, 40]},
            {"op": "fill", "ramp": "stone", "level": 2, "depth": 240, "rect": [11, 14, 21, 40]},
            {"op": "fill", "ramp": "stone", "level": 2, "depth": 232, "rect": [21, 26, 29, 40]},
            # Светлая кромка там, где солнце задевает срез кладки. Один пиксель, не два:
            # полоса в две строки во всю ширину читается как отдельная деталь.
            {"op": "fill", "ramp": "stone", "level": 4, "depth": 242, "rect": [3, 22, 11, 23]},
            {"op": "fill", "ramp": "stone", "level": 4, "depth": 246, "rect": [11, 14, 21, 15]},
            {"op": "fill", "ramp": "stone", "level": 3, "depth": 238, "rect": [21, 26, 29, 27]},
            # Швы: тёмный пиксель и светлый под ним. Тот же приём, что в `_wall_boards` —
            # два соседних пикселя противоположной яркости превращают одну заливку в
            # отдельные камни.
            {"op": "fill", "ramp": "dark_stone", "level": 0, "depth": 230, "rect": [11, 20, 21, 21]},
            {"op": "fill", "ramp": "dark_stone", "level": 0, "depth": 230, "rect": [3, 30, 29, 31]},
            {"op": "fill", "ramp": "stone", "level": 3, "depth": 234, "rect": [3, 31, 29, 32]},
            {"op": "fill", "ramp": "dark_stone", "level": 0, "depth": 230, "rect": [3, 36, 29, 37]},
            {"op": "fill", "ramp": "stone", "level": 3, "depth": 234, "rect": [3, 37, 29, 38]},
            # Одна асимметричная трещина, идущая вдоль формы. Две параллельные читались бы
            # как машина — тот же урок, что записан в `cliff`.
            {"op": "line", "ramp": "dark_stone", "x0": 16, "y0": 16, "x1": 13, "y1": 30, "level": 0, "thickness": 1, "depth": 214},
            # Осыпь у основания кусками, а не по пикселю, и клок мха. Пиксельный шум любой
            # плотности читается как рябь телевизора.
            {"op": "blob", "ramp": "stone", "seed": 61, "x": 6, "y": 38, "radius": 3.0, "wobble": 0.30, "level": 1, "depth": 208, "dome": False},
            {"op": "blob", "ramp": "stone", "seed": 62, "x": 26, "y": 38, "radius": 2.4, "wobble": 0.32, "level": 1, "depth": 206, "dome": False},
            {"op": "blob", "ramp": "leaf", "seed": 63, "x": 12, "y": 34, "radius": 2.2, "wobble": 0.40, "level": 1, "depth": 232},
            {"op": "outline", "ramp": "shadow", "level": 0, "alpha": 235},
            {"op": "contact_shadow", "rows": 2, "amount": 0.32},
            anchor_y=0,
        ),
```

`anchor_y=0` — стена стоит на кромке тайла, как `wall_wood` и `wall_stone`.
Положительный `anchor_y` опускает спрайт ниже кромки, то есть «вкапывает» его в
землю; так сделаны трава (6), дерево (8), кактус (4).

### 2.7 Шаг 6 — привязки

Там же, в `recipes.py`:

```python
TILE_GROUND: dict[int, str] = {
    ...
    Tile.CACTUS: "sand",
    Tile.RUINED_WALL: "bare_ground",
}

TILE_PROP: dict[int, str] = {
    ...
    Tile.CACTUS: "cactus",
    Tile.RUINED_WALL: "ruined_wall",
}
```

`TILE_GROUND` обязателен для каждого тайла без исключений, включая блокирующие:
проп рисуется на слое над меш-рельефом, и если у клетки нет ковра, дерево будет
висеть над дырой. Тест `test_every_tile_has_ground_beneath_it` перебирает всё
перечисление `Tile` и падает на пропущенном.

`TILE_ANIMATION` трогать не нужно: анимируется только вода, и то ground-слоем.
Всё остальное, что должно двигаться, двигается пропсом на слое выше.

## 3. Как добавить новый декоративный проп

Декор — это то, у чего нет своего тайла и нет влияния на геймплей: фонтан,
прилавок, лавка, фонарь, костёр, вывеска. Фонарём нельзя заблокировать проход.
Из этого следует важная вещь: декор целиком выводится на клиенте и не проходит
паритетных тестов. Линия проведена сознательно — всё, в чём симуляция может
ошибиться, дублируется и сверяется, а то, в чём не может, нет.

Сейчас в `DECOR_RECIPES` двенадцать ключей, и все двенадцать расставлены по хабу:
`fountain`, `market_stall`, `well`, `bench`, `barrel`, `sacks`, `planter`, `sign`,
`lantern`, `banner`, `crate`, `campfire`.

Полный пример: поилка — каменное корыто с водой, для двора за площадью.

### 3.1 Рецепт

В `PROP_RECIPES` (декор живёт там же, где пропсы):

```python
        _prop(
            "trough",
            24,
            # Сделанный предмет, поэтому прямоугольники, а не блобы. У `lantern` этот урок
            # записан прямым текстом: три концентрических вихляющих кольца на палке
            # читаются как ручное зеркало, потому что светлое кольцо вокруг светлого
            # центра — это линза.
            {"op": "fill", "ramp": "stone", "level": 2, "depth": 200, "rect": [2, 12, 30, 24]},
            {"op": "fill", "ramp": "stone", "level": 1, "depth": 196, "rect": [2, 21, 30, 24]},
            # Бортик: верхние строки светлее корпуса, самая верхняя — с отступом внутрь.
            # Горизонтальная полоса сверху говорит, что вы смотрите на предмет сбоку.
            {"op": "fill", "ramp": "stone", "level": 3, "depth": 206, "rect": [2, 12, 30, 14]},
            {"op": "fill", "ramp": "stone", "level": 4, "depth": 208, "rect": [4, 12, 28, 13]},
            # Вода с отступом от бортика, чтобы камень читался как стенка, которая её
            # держит, а не как кольцо, нарисованное поверх. Ровно то же сделано в
            # `fountain`. Заливка обязательна до `ripple`: гребни ложатся только на уже
            # непрозрачные пиксели.
            {"op": "fill", "ramp": "water", "level": 2, "depth": 190, "rect": [5, 14, 27, 18]},
            {"op": "dither", "ramp": "water", "from": 3, "to": 1, "rect": [5, 14, 27, 18]},
            {"op": "ripple", "ramp": "water", "level": 4, "band": 1, "rect": [5, 14, 27, 18]},
            {"op": "outline", "ramp": "shadow", "level": 0, "alpha": 225},
            {"op": "contact_shadow", "rows": 2, "amount": 0.32},
            frames=4,
            anchor_y=0,
        ),
```

Числа здесь — отправная точка, а не истина. Все существующие рецепты доводились
одинаково: напечатать `probe_atelier.py`, посмотреть на `props-big.png`,
подвинуть координаты, повторить. Три-четыре круга — норма.

### 3.2 Объявить его декором

```python
DECOR_RECIPES = (
    "lantern",
    "banner",
    "crate",
    "campfire",
    "fountain",
    "market_stall",
    "well",
    "bench",
    "barrel",
    "sacks",
    "planter",
    "sign",
    "trough",
)
```

После этого поилка попадёт в атлас, появится в редакторе и будет доступна клиенту
по ключу `trough`. И **не появится в мире**, пока её кто-нибудь не поставит.

### 3.3 Поставить его в мир

Расстановка живёт в `age/frontend/src/render/decor.ts`. Там три таблицы
неподвижных предметов — `PLAZA`, `MARKET`, `YARD` — плюс одно правило для
уличных фонарей. Координаты в таблицах **локальные для хаба**: начало отсчёта в
центре площади, отрицательный `y` — к северу от фонтана, отрицательный `x` — к
западу. То есть таблица читается как план площади, и добавить предмет — это одна
строка:

```typescript
const YARD: readonly Fixture[] = [
  { key: 'well', localX: -9, localY: 9 },
  { key: 'trough', localX: -5, localY: 10 },
  { key: 'campfire', localX: 8, localY: 8, light: 'campfire' },
```

Таблица, а не правило, — потому что первая версия расставляла хаб арифметикой по
модулю и читалась как пустое поле с фонарными столбами. Это разобрано в разделе
[11.7](#117-композиция-важнее-количества), и прочитать его стоит до того, как
дописывать строки: место, куда вы поставите поилку, определяет больше, чем её
рецепт. Правилом осталось только уличное освещение (`STREET_SPACING = 12`,
`LANTERN_SPACING = 6`).

Что происходит с числами дальше: `decorFor` отбирает предметы, попавшие в
границы чанка, и переводит их в мировые тайлы, прибавляя `+0.5` по `x` и `+1` по
`y`. Половина тайла по горизонтали — центр клетки, целый тайл вниз — её нижняя
кромка: `PropLayer.addDecor` центрирует спрайт по `x` и ставит его основание на
`y`, а сортировка по глубине ждёт основание именно там.

Кадр декору выдаёт та же общая переменная `waterFrame`, что и рельефу, так что
анимированный декор идёт на шести кадрах в секунду и в такт со всем остальным
(раздел [7.3](#73-частота-кадров-честная-оговорка)).

Это правка кода клиента, а не данных, и требует `npm run build`. Настоящее
решение — расставлять декор в LDtk и хранить его рядом с наложением рельефа
(раздел [9](#9-импорт-из-внешних-редакторов) и пункт 3 в разделе 12).

### 3.4 Если декор должен светить

`Placement.light` — это `'lantern' | 'campfire' | undefined`, и параметры
источников лежат в `EMITTERS` в `age/frontend/src/render/scene.ts`:

```typescript
  lantern: { radius: 170, colour: [1, 0.87, 0.62], intensity: 1.15, height: 46, lift: 34, flicker: 0.045, flickerHz: 2.1 },
  campfire: { radius: 140, colour: [1, 0.68, 0.34], intensity: 1.4, height: 18, lift: 10, flicker: 0.17, flickerHz: 8.7 },
```

Здесь важны два поля, которые легко понять неправильно. `lift` поднимает
источник вверх по спрайту к тому месту, где на самом деле пламя, — иначе фонарь
освещает землю под собственным столбом и больше ничего. `height` — высота
источника над плоскостью земли; при нуле направление на свет лежит в той же
плоскости, что и нормали, почти ничего не затеняется, и карта нормалей
пропадает даром.

Новый вид источника — это новый ключ в `EMITTERS` и расширение объединения
типов в `decor.ts`. Тоже код.

## 4. Справочник операций Atelier

Операции — в `age/atelier/canvas.py`, разбор JSON-шага — в `_apply` в
`age/atelier/recipes.py`. Одно исключение: `ripple` живёт не в `canvas.py`, а
рядом с разбором, функцией `_ripple` в `recipes.py`. Ниже — точные имена ключей
JSON и значения по умолчанию, как их читает `_apply`. Имена в JSON и имена
аргументов Python местами различаются (`from`/`from_level`,
`litFromLeft`/`lit_from_left`), и именно JSON-имена вы пишете в рецепте.

| `op` | Ключи JSON (значение по умолчанию) | Для чего |
| --- | --- | --- |
| `fill` | `ramp` (`soil`), `level` (2), `depth` (0), `material` (0), `rect` | плоская заливка — основа под всё остальное |
| `scatter` | `ramp` (`soil`), `seed` (0), `density` (0.1), `level` (1), `depth` (нет), `material` (нет), `onlyOnOpaque` (`true`) | одиночные пиксели в хешированных позициях: текстура земли, лишай, крупа |
| `dither` | `ramp` (`soil`), `from` (1), `to` (3), `vertical` (`true`), `rect` | упорядоченный градиент между двумя оттенками |
| `blob` | `ramp` (`leaf`), `seed` (0), `x` (16), `y` (16), `radius` (8), `wobble` (0.35), `level` (2), `depth` (160), `material` (0), `dome` (`true`) | органическая масса: кроны, камни, кусты |
| `column` | `ramp` (`wood`), `rect` (весь холст), `level` (2), `depth` (200), `material` (0), `litFromLeft` (`true`) | вертикальный ствол со светлой и тёмной стороной |
| `line` | `ramp` (`wood`), `x0` `y0` `x1` `y1` (0), `level` (2), `thickness` (1), `depth` (120), `material` (0) | линия Брезенхэма: ветки, верёвки, жерди, трещины |
| `outline` | `ramp` (`shadow`), `level` (1), `alpha` (235), `onlyBottom` (`false`) | тёмный контур по силуэту |
| `contact_shadow` | `rows` (2), `amount` (0.35) | притемнение нижних строк: смыкание с землёй |
| `mirror` | — | отражает левую половину в правую |
| `sway` | `pivotRow` (высота − 1), `amplitude` (1.0) | **анимация**: сдвиг строк выше опорной — ветер |
| `bob` | `amplitude` (1.0) | **анимация**: весь спрайт вверх-вниз |
| `shift` | `amplitude` (1.0), `rect` (весь холст) | **анимация**: часть холста ходит боком как жёсткое тело — вывеска на кронштейне |
| `glow` | `amount` (0.2), `rect` (весь холст) | **анимация**: яркость нарисованного дышит — пламя за стеклом, брызги фонтана |
| `ripple` | `ramp` (`water`), `level` (4), `band` (2), `rect` (весь холст) | **анимация**: бегущие гребни — вода |
| `flicker` | `aboveRow` (высота), `amount` (0.3) | **анимация**: выедание силуэта — огонь |

### 4.1 Что надо знать помимо таблицы

**`rect` — это `[x0, y0, x1, y1]`, правая и нижняя границы не включаются.**
Редактор подписывает поля «left, top, right, bottom», но это `range(y0, y1)`:
`[x, 15, x + 1, 44]` — колонка шириной один пиксель. Так набраны швы досок в
`_wall_boards`.

**`fill` всегда пишет `depth`, и по умолчанию нолём.** Это самая частая
неочевидная ошибка: заливка без явного `depth` посреди пропа сносит рельеф в
своём прямоугольнике в ноль, и освещение делает там плоское пятно. У ground это
нормально, у пропа почти всегда нет. То же с `material`: `fill`, `blob`,
`column` и `line` по умолчанию пишут `material: 0`.

**`dither` не трогает `depth` вообще**, и `material` у него `_apply` не читает —
ключ в шаге будет молча проигнорирован. `scatter` без `depth`/`material`
оставляет их как были. `contact_shadow` перерисовывает цвет, не касаясь высоты.
`mirror` копирует все три канала. `ripple` сохраняет высоту под гребнем.

**`outline` пишет `depth: 0`.** Это правильно: кромка — не поверхность, и
рельефа у неё быть не должно.

**Глубина и материал пишутся только там, где альфа ≥ 128.** Мягкий край — не
поверхность, и если считать его поверхностью, у каждого спрайта появляется
ореол из ложных нормалей.

**`thickness` у `line` округляется вверх до нечётного.** Внутри
`reach = thickness // 2`, и кисть получается `2 * reach + 1` пикселей: 1 → 1, 2
и 3 → 3, 4 и 5 → 5. Многие рецепты пишут `thickness: 2` и получают три пикселя —
так и задумано, но знать об этом надо.

**`level` у `blob` и `column` — это средний оттенок, а не единственный.** `blob`
ставит `level + 1` внутри (ближе 0.45 радиуса) и `level − 1` по краю (дальше
0.86). `column` даёт `level + 1` на первой трети ширины и `level − 1` на
последних 28 процентах, а при `litFromLeft: false` — наоборот. Поэтому `level: 0` у
блоба даёт почти чёрный край, `level: 4` — почти белую середину, и оба обычно не
то, что нужно.

**`sway` и `bob` возвращают новый холст.** Всё, что нарисовано после них,
попадёт уже на сдвинутую копию. Практически это значит, что они идут последними
шагами рецепта — посмотрите на `tall_grass`, `bush`, `tree`, `banner`,
`market_stall`. Остальные три анимации работают на месте, но ставятся последними
по той же причине, что и они: `flicker` иначе съест заодно камни и брёвна костра,
`glow` подсветит то, что не должно светиться, а `shift` увезёт вместе с вывеской
её кронштейн.

**`shift` роняет пиксели, вышедшие за `rect`.** Он не заворачивает их и не
расширяет область, так что в прямоугольнике надо оставить запас по горизонтали на
всю амплитуду. У `sign` полоса сдвига — `[7, 10, 29, 27]` при холсте шириной 32 и
амплитуде 1.

**`glow` умножает, а не прибавляет.** Тёмный пиксель остаётся тёмным, светлеет
только то, что уже светлое. Прибавка константы вымыла бы теневую сторону корпуса
фонаря в серое. Высоту и материал `glow` сохраняет.

**`ripple` кладёт гребни только на непрозрачные пиксели.** На ground это каждый
пиксель, и проверка бесплатна, но первый проп с рябью — фонтан — получился с
гребнями, бегущими по пустоте рядом с ним, и издалека это читалось как крылья.
Отсюда и `rect` у `ripple`: воду надо и залить, и ограничить.

**`scatter` с `onlyOnOpaque: false` брызжет за силуэт.** Для ground это
безразлично (там всё залито), для пропа получается прямоугольник крупы вокруг
объекта. Тест `test_props_have_transparent_backgrounds` проверяет левый верхний
угол и ловит именно это.

**Ластика нет.** `Canvas.clear` в Python есть и активно используется внутри
`character.py` (скругление челюсти, купол черепа), но ни одна операция рецепта
его не выставляет. Силуэт в рецепте можно только не нарисовать — набрать
неровный край из отдельных прямоугольников и блобов, как это сделано в `cliff` и
в `ruined_wall` выше. Единственная лазейка: `flicker` в рецепте с одним кадром
детерминированно выедает край и работает как эрозия. Приём рабочий, но
неочевидный, и в существующих рецептах не применён.

**У `flicker` собственный `seed` не читается.** `_apply` собирает его сид как
`seed ^ (frame * 0x27D4EB2D)` — из сида шага в рецепте и номера кадра. Поле
`Seed`, которое редактор показывает для `flicker`, не влияет ни на что. Чтобы
получить другой рисунок пламени, двигайте `flicker` по списку шагов: его позиция
входит в сид (`seed ^ (index * 0x9E37)`).

**Дизеринг упорядоченный, матрицей Байера 4×4, и это принципиально.**
Диффузия ошибки (Флойд-Стейнберг) даёт крупу, которая **ползёт** при движении
спрайта; пиксель-арту нужен узор, стоящий на месте.

### 4.2 Ограничения на рецепт из браузера

`Recipe.from_json` не доверяет входу, потому что он приходит из браузера:
ширина и высота зажимаются в 1–256, число шагов — до 64, `frames` — 1–16,
`anchorY` — от −64 до 64, `key` — 64 символа, `label` — 64, `kind` — 16. Тело
запроса на печать — не больше 64 КиБ, на импорт — не больше 4 МиБ. Рецепт,
объявивший себя 40000 пикселей в квадрате, печатался бы до смерти воркера.

## 5. Палитра и рампы

`age/atelier/palette.py`. Пиксель-артовый вид берётся не из разрешения, а из
цветовой дисциплины: маленькая палитра и затенение по **лестнице**, а не
умножением цвета на 0.6. Умножение даёт мутные серые тени.

### 5.1 Как строится рампа

Рампа — это `RAMP_STEPS = 5` оттенков, от тёмного к светлому, сгенерированных из
одного базового цвета по трём правилам:

**Сдвиг тона.** По рампе тон едет, а не только светлота:
`SHADOW_HUE_SHIFT = -0.022`, `HIGHLIGHT_HUE_SHIFT = 0.018` (в оборотах тона,
примерно восемь градусов на шаг). Это самая большая разница между
сгенерированной рампой, которая выглядит плоско, и той, которая выглядит
написанной.

Здесь надо оговорить одну вещь, потому что документация проекта сама себе
противоречит. Докстринги в `palette.py` и обзор в `art-pipeline.md` описывают
классическое правило: тени к синему, блики к жёлтому. В коде же это простая
добавка к тону в модели HLS, а не поворот к цели, и для тёплых материалов
проекта — земли, дерева, кожи — отрицательная добавка тянет тени **к красному**,
а не к синему. Комментарий к тесту в `tests/test_age_atelier.py` говорит об этом
прямо: «эта палитра тянет тени к красному, а блики к жёлтому», и утверждает тест
только то, что тон движется и движется монотонно в одну сторону. Для холодных
рамп (`water`, `deep_water`) та же добавка уводит тени к бирюзовому. Практически
это работает: рампы выглядят живыми. Но если вы будете подбирать базовый цвет,
рассчитывая на «тени уйдут в синеву», результат вас удивит — смотрите на
образцы в редакторе.

Величины маленькие не от робости. Сдвиг — фиксированная добавка, и тёплым тонам
разворачиваться некуда: оранжевый стоит градусов в двадцати от красного, так что
шаг побольше уводит кожу через красный в пурпур. При 0.055 загар `bc8a64` в тени
становился `a7463b`, что на лице читается как травма. Холодные тона терпят
гораздо больше, но константа должна годиться для самого узкого случая.

**Насыщенность растёт в тень.** Тёмный участок в тени **цветнее** освещённого, а
не бледнее (`saturation_pull = 0.09`). Сделать наоборот — и рампа выглядит как
ползунок яркости.

**Лестница светлоты нелинейна:** `LIGHTNESS_LADDER = (-2.0, -1.05, 0.0, 0.90, 1.65)`
при `spread = 0.115`, светлота зажата в 0.04…0.93. Крайние шаги сжаты, чтобы верх
не доходил до белого, а низ — до чёрного. Линейная лестница выбивала каждый блик
на цвете средней светлоты почти в белый, и весь тайлсет сплющивался в блик.

### 5.2 Уровни

Индекс 2 — база. `Ramp.shade(level)` зажимает индекс, так что можно затенять «за
край» без проверок: `level: -1` даст 0, `level: 7` — 4.

| 0 | глубокая тень | контуры, швы, глазницы, самые тёмные щели |

### 5.4 Что читается как форма, а что как шум

Правила, выведенные из уже написанных рецептов:

- **Два соседних уровня — это градация. Разрыв в два и больше — это граница
  плоскости.** Если нужно, чтобы читались отдельные камни или доски, ставьте
  рядом уровни 0 и 3, а не 2 и 3. Именно так работают швы в `_wall_boards`.
- **Уровни 0 и 4 — по одному пикселю.** Блик во всю ширину в две строки читается
  как отдельная деталь (в `character.py` это записано так: две строки светлой
  кожи во всю ширину лба читаются как головная повязка).
- **Разница в один уровень на площади в один пиксель не читается вообще.** Если
  деталь размером в пиксель должна быть видна, ей нужен контраст в два-три
  уровня или контур.
- **Три уровня на объект — это уже объёмный объект.** Ствол дерева — это
  `column` с `level: 2`, то есть три оттенка на четырёх пикселях, и этого
  хватает.
- **Смена рампы важнее смены уровня.** Мох на камне — это `leaf` поверх `stone`,
  а не `stone` уровня 3. Одна рампа на весь объект читается как один материал,
  освещённый по-разному, — этого свойства и добивается монотонность рампы по
  светлоте.

## 6. Как рисовать нормали и почему

### 6.1 Что вообще происходит

Ручное рисование карты нормалей на каждый спрайт — не та работа, которую можно
всерьёз просить у автора. Поэтому ателье рисует **высоту**, а нормали выводит из
неё. Вопрос «насколько это выступает» — вопрос про форму, а не про векторное
поле, и это единственный способ, которым сгенерированный спрайт вообще может
получить правдоподобные нормали.

`age/atelier/normals.py` берёт градиент Собеля по каналу `depth` и упаковывает
результат так, как ждёт любой 2D-движок: `x` в красный, `y` в зелёный, `z` в
синий, `[-1, 1]` в `[0, 255]`, плоская поверхность — `(128, 128, 255)`.

Собель, а не двухтактная разность: пиксель-арт состоит из одно-пиксельных
уступов, и разность по двум отсчётам превращает каждый из них в жёсткий залом.

`DEFAULT_STRENGTH = 2.4` — насколько сильно перепад высоты наклоняет
поверхность. Значение выбрано так, чтобы брусчатка на тайле 32 пикселя была
видна под движущимся светом, а плоская земля не выглядела гофрированным
железом.

Две детали, которые легко сделать неправильно и трудно заметить:

- **Знак зелёного канала.** Соглашение OpenGL, `+y` вверх по экрану, потому что
  именно так его читает шейдер в `frontend/src/render/lighting.ts`. Перевёрнутое
  освещение выглядит *почти* правильно, и это гораздо труднее увидеть, чем
  очевидно сломанное. Поэтому на знак есть тест.
- **Заворот на краях.** Бесшовные ground-тайлы сэмплируются с заворотом, а не с
  зажимом. Зажим оставляет однопиксельный хребет ровно там, где тайл
  повторяется, и это видно как сетка поверх всего мира. Отвечает за это флаг
  `seamless` в рецепте, который `_ground` ставит автоматически.

Прозрачные пиксели получают плоскую нормаль, чтобы неосвещённый фон не
подхватывал рельеф соседа.

### 6.2 Шкала глубин, которой держится проект

Единого закона нет, но есть сложившаяся шкала, и её стоит соблюдать, иначе один
проп будет ловить свет иначе, чем стоящий рядом.

| Что | `depth` |
| --- | --- |
| ground: крупа на земле, траве, песке | 2–10 |
| ground: галька в гравии | 30 |
| ground: брусчатка | 90 |
| ground: швы между досками | 0 |
| травинки | 40 |
| листва куста, крона дерева | 150–190 |
| стойки, жерди, забор | 120–160 |
| ствол дерева | 210 |
| камень | 200–230 |
| корпус фонаря | 170–216 |
| ящик, бочка | 190–212 |
| мешки, ящик с растениями | 165–182 |
| лавка | 150–194 |
| вывеска (столб → щит) | 160 → 214 |
| чаша фонтана и вода в ней | 190–238 |
| кладка колодца, кровля | 180–240 |
| прилавок (стойки → навес) | 150 → 244 |
| деревянная стена | 228–240 |
| каменная стена | 250 |
| утёс | 232–254 |
| камни и брёвна костра | 30–70, пламя 110–120 |

Читается это так: земля — почти ноль, стоящие предметы — от 120, вертикальные
стены и скалы — под 250. Пламя специально низкое: оно не поверхность, и лишний
рельеф на нём выглядит как жестяной огонь.

### 6.3 Как рисовать высоту, чтобы свет был правильным

- **Купол делает камень камнем.** `blob` с `dome: true` формует высоту как
  полусферу (`depth * sqrt(1 - ratio²)`), и разница между освещённым валуном и
  освещённой наклейкой валуна — именно в этом. `dome: false` даёт плоскую
  плиту постоянной высоты, и это правильный выбор для фасетов утёса: каждая
  фасета — плоскость, повёрнутая по-своему, и их общие рёбра сами становятся
  линиями, описывающими форму.
- **`column` уже гнёт высоту по синусу** (`depth * (0.55 + 0.45 * sin(pi * position))`),
  так что столб получает круглую нормаль без всяких усилий.
- **Плоское плато одинаковой высоты — это нормально.** Внутри плоской
  поверхности нормали и должны быть плоскими; форму описывают её **края**. Не
  надо «текстурировать» высоту, чтобы стена перестала быть плоской: стена
  плоская.
- **Не шумите по высоте.** Пиксельный шум в `depth` даёт пиксельный шум в
  нормалях, а это на экране рябь, которая ползёт вместе со светом. Разброс в
  2–10 единиц на ground — предел, и он там сделан именно затем, чтобы земля
  ловила скользящий свет и не мерцала.
- **Помните про `fill` без `depth`.** Он пишет ноль. Заливка деталью поверх
  готового рельефа без явной высоты пробивает в нём плоскую дыру.
- **Контур на нулевой высоте — это правильно.** `outline` ставит `depth: 0`, и
  тёмная кромка получается неосвещаемой. Так и надо: кромка — это условность
  пиксель-арта, а не поверхность.
- **Свет должен быть поднят.** В `EMITTERS` есть `height`, и при нуле карта
  нормалей не даёт ничего. Если ваш новый источник света «не работает», сначала
  проверьте `height`, а не рецепт.

Шейдер применяет half-Lambert (`lambert * 0.75 + 0.25`): чистый Ламберт оставляет
всё, отвёрнутое от света, полностью чёрным, а на 2D-сцене это читается как
дырка, а не как тень. Так что абсолютно тёмных мест не будет — и не надо
пытаться получить их через высоту.

Эталон освещения есть на Python: `normals.lambert` — это то, что шейдер делает
на пиксель. Именно поэтому освещение вообще можно покрыть тестом: тест
утверждает, что стена, освещённая слева, светлее с левой стороны, а это ровно
тот баг, который даёт перевёрнутый зелёный канал.

## 7. Анимация

### 7.1 Как это устроено

`frames` в рецепте больше единицы делает его анимированным. `bake` получает
номер кадра и считает две величины:

```python
index_in_loop = frame % recipe.frames
phase = index_in_loop / recipe.frames if recipe.frames > 1 else 0.0
wave = math.sin(phase * math.tau)
```

`phase` — положение кадра в цикле, `[0, 1)`. `wave` — синус от него, и
анимированные операции берут именно синус, чтобы цикл **замыкался сам на себя**.
Анимация, которая прыгает на стыке, — самый частый способ, которым процедурная
анимация спрайтов выглядит неправильно.

Анимируются шесть операций, и каждая появилась потому, что предыдущих не хватило
на конкретный предмет:

- `sway` — сдвигает строки в сторону на `amplitude * wave`, тем сильнее, чем
  выше строка над `pivotRow`, причём сдвиг **квадратичен** по высоте, так что
  основание стоит на месте, а верхушка ходит больше всего. Это то, как гнётся
  стебель, укоренённый в земле. Трава, знамёна, листва, навес прилавка, цветы в
  ящике.
- `bob` — переносит весь холст по вертикали на `round(amplitude * wave)`.
  Парящие предметы. В рецептах проекта сейчас **не используется**: единственный
  претендент, фонарь, от него отказался (см. ниже).
- `shift` — переносит боком, как жёсткое тело, только пиксели внутри `rect`.
  Предмет, подвешенный за верх: у него ходит низ, а не верх, то есть ровно
  наоборот по сравнению с `sway`. Вывеска на кронштейне.
- `glow` — умножает яркость нарисованного на `1 + amount * wave` внутри `rect`.
  Предмет, у которого меняется не форма, а то, насколько сильно он светится:
  пламя за стеклом фонаря, брызги фонтана.
- `ripple` — прокатывает два гребня разной длины волны, у каждого целое число
  периодов по ширине области, чтобы они по-прежнему сходились на шве. Вода.
  Гребни *накладываются*, а не деформируют тайл: деформация была бы проще в
  написании и ломала бы бесшовность, что на открытой воде видно сразу.
- `flicker` — стирает набор пикселей выше строки `aboveRow`, выбранный по хешу от
  позиции и сида, причём только те, над которыми пусто, то есть только по
  силуэту. Огонь.

### 7.2 Ловушки, которые уже сработали

**`sway` не годится для огня.** Это записано в коде дважды, в `canvas.py` и в
рецепте `campfire`, и стоило одного сломанного костра. Причин две. Первая: огонь
не изгибается как твёрдое тело — между двумя кадрами пламени меняется его
**контур**, а не наклон, поэтому сдвиг читается как флаг на ветру. Вторая
конкретнее: квадратичное затухание `sway` делает сдвиг пренебрежимо малым
везде, кроме самого верха холста, а у костра пламя в середине спрайта — все
четыре кадра испеклись **побайтно одинаковыми**. Проба арта это и поймала.

**`sway` не годится и для вывески — по противоположной причине.** Вывеска висит
на кронштейне, то есть закреплена **сверху**, а `sway` держит на месте низ. Первая
версия `sign` всё равно использовала `sway`, с опорной строкой ниже щита, и
квадратичное затухание дало щиту сдвиг меньше половины пикселя: все четыре кадра
испеклись одинаковыми, и это опять поймал тест. Щит на двух цепях почти не
деформируется — он переносится, и для этого есть `shift`.

**`bob` не годится для фонаря на столбе.** `bob` двигает весь холст, поэтому
столб, колпак и кронштейн подпрыгивали вместе с лампой, как воздушный шарик на
нитке. В комментарии к `glow` это названо самой очевидно неправильной анимацией
в сцене. У висящей на столбе лампы не двигается ничего — меняется то, насколько
сильно горит пламя, и это `glow` по прямоугольнику со стеклом.

**`frames: 2` вместе с `sway`, `bob`, `shift` или `glow` даёт два одинаковых
кадра.** Все четыре читают `wave`, а при двух кадрах фазы 0 и 0.5, и `sin(0)` и
`sin(pi)` — оба ноль. Тест `test_animated_recipes_differ_between_frames` падает, и
это правильно: два одинаковых кадра — просто потраченное место в атласе. Работают
четыре кадра (фазы 0, ¼, ½, ¾ дают множители 0, +1, 0, −1) или три. `flicker` от
этого не страдает: у него номер кадра идёт в сид, а не в амплитуду; `ripple`
берёт фазу напрямую, а не через синус.

**Иногда четырёх кадров мало.** У `lantern` и `fountain` их шесть. При четырёх
пульсация `glow` проходит через ноль, максимум и минимум и читается как мигание
между двумя состояниями; чтобы это выглядело горением, у волны должна быть видимая
середина и на подъёме, и на спуске.

**Анимация должна замыкаться.** Отсюда синус, и отсюда же то, что `ripple`
сдвигает гребни на `phase * span`, где `span` — высота области, и берёт остаток по
ней: при фазе, подходящей к единице, сдвиг подходит к высоте области, то есть к
нулю.

**Контур ставится до наклона.** Если `outline` идёт после `sway`, он обведёт уже
наклонённый спрайт заново — иногда это то, что нужно, но чаще нет: в `bush`,
`sapling`, `tree` и `market_stall` контур обводится **до** анимирующего шага, и
качается вместе с силуэтом, а не перерисовывается на каждом кадре.

**Каждый кадр — отдельная запись в атласе.** Страница одна, 1024×1024, и
переполнение не растит её молча, а падает с ошибкой на этапе сборки (это
специально: текстура, которая не загрузится на чьём-то ноутбуке, хуже, чем
падение при сборке). Сейчас занято 78 кадров. Анимировать «на всякий случай» —
это платить местом.

### 7.3 Частота кадров: честная оговорка

`TILE_ANIMATION` объявляет частоту: вода 6 кадров в секунду, глубокая вода 4.
Клиент эту частоту **не соблюдает**. `render/scene.ts` считает один общий
счётчик `waterFrame = Math.floor(elapsed * 6)` и раздаёт его и рельефу, и
пропсам, а `atlas.animationRate(tile)` используется только как булев признак
«анимируется ли». То есть глубокая вода идёт на 6 кадрах вместо 4, и деревья
качаются на тех же 6.

Практический вывод: делайте анимации в расчёте на 6 кадров в секунду и на общий
для всей сцены фазовый счётчик. Два костра рядом будут в такт (у источников
света разброс фазы есть, у спрайтов — нет).

## 8. Как рисовать персонажа

### 8.1 Почему персонаж — не рецепт

Дерево — это куча блобов, и кучу можно описать декларативно. Цикл ходьбы — это
**оснастка**: положение конечности есть функция кадра, и каждая часть должна
оставаться прикреплённой к той, что выше. Поэтому `age/atelier/character.py` —
параметризованный генератор, а не список шагов.

### 8.2 Пять байт внешности

`Appearance` в `age/domain/entities.py` — это пять маленьких чисел, а не URL:
новый персонаж стоит семь байт на проводе вместо загрузки текстуры. Ателье
разбирает их так:

| Байт | Как читается | Что выбирает |
| --- | --- | --- |
| `body` | `body % 3` | телосложение: полуширина плеч 7, 8, 9 |
| `hair` | `hair % 3` и `hair % 4` | **одновременно** цвет волос (из 3 рамп) и стиль (из 4) |
| `palette` | `palette % 3` | кожа: `skin_light`, `skin_mid`, `skin_dark` |
| `outfit` | `outfit % 6` | одежда: `cloth`, `leaf`, `metal`, `wood`, `gold`, `brick` |
| `outfit` | `outfit % 6` (вторая таблица) | штаны: `wood`, `soil`, `dark_stone`, `dark_stone`, `wood`, `soil` |
| `accent` | `accent % 3` из отфильтрованного списка | акцент (пояс, обувь, манжета, гарда): `gold`, `metal`, `ember`, `cloth` **минус рампа одежды** |

Про фильтр в последней строке стоит знать, потому что он появился после провала.
`ACCENT_RAMPS` и `OUTFIT_RAMPS` пересекаются по `cloth`, `metal` и `gold`, так что
простой остаток по модулю попадал в рампу одежды примерно у четверти внешностей —
и в том числе у внешности по умолчанию, той самой, которая идёт на все скриншоты
и во все тестовые заглушки. Акцент цвета одежды — это не акцент: пояс, обе
манжеты и обувь растворяются в тунике, а вместе с ними фигура теряет талию и
кисти, то есть ровно те детали, которые отделяют её части друг от друга. Поэтому
`accent_ramp` выбирает из списка, из которого рампа одежды выброшена.

Штаны не берут рампу одежды, и это следствие провала: когда торс, руки и ноги
были одного тона, персонаж носил комбинезон, у фигуры не было талии, а цикл
ходьбы становился невидимым — нельзя увидеть, как нога идёт вперёд, если она
того же цвета, что нога за ней. Все штанные рампы темнее и глуше любой из
одёжных, что заодно похоже на то, как устроена настоящая одежда.

Диапазоны ползунков титульный экран (`frontend/src/ui/TitleScreen.tsx`) **берёт с
сервера**, из поля `appearanceRanges` в `/api/world`, а числа считает
`APPEARANCE_RANGES` в `character.py` прямо из длин таблиц. Так сделано после того,
как копия в TypeScript разъехалась: экран предлагал пять значений для волос и пять
для кожи против двенадцати и трёх у бейкера, и ползунки то повторяли внешности, то
скрывали их. Из таблиц эти числа не читаются глазами — `hair` кормит **два**
разных модуля, поэтому различных видов у него двенадцать (три цвета × четыре
стиля), а не три и не четыре.

Одно исключение осталось, и оно намеренное: `accent` объявлен как 4, хотя список
после выброса рампы одежды бывает длиной 3. Это верхняя граница, так что для
одежды, делящей рампу с акцентом, последняя остановка ползунка повторяет первую.
Альтернатива — диапазон, который меняется на ходу при движении соседнего ползунка,
что для игрока выглядит как поломка.

Значения в TypeScript остались как форма для первой отрисовки, до того как ответ
`/api/world` дойдёт, и они приведены в соответствие с таблицами.

### 8.3 Пропорции

Каждая часть читает геометрию из общих констант, а не считает её у себя. Когда
арифметика была разбросана по функциям, она разъехалась, и голова стала шириной
с грудь — именно это превращает маленький спрайт в тотемный столб.

```python
SPRITE_WIDTH = 32        # тело занимает 22, остальное — запас
SPRITE_HEIGHT = 48
FEET_ROW = 45            # где стоят ноги, считая от верха

CROWN_ROW = 4            # верх волос
HEAD_TOP = 6
HEAD_HEIGHT = 12
HEAD_HALF_WIDTH = 6      # 12 пикселей, всё равно уже плеч
NECK_ROW = 17
SHOULDER_ROW = 19
WAIST_ROW = 28
HIP_ROW = 31
SHOULDER_HALF_WIDTHS = (6, 7, 8)
ARM_DROP = 2             # насколько ниже линии плеч начинается рука
ARM_LENGTH = 11          # от плеча до кончиков пальцев, рука висит до бедра
ARM_WIDTH = 3
LEG_WIDTH = 4
```

Три числа здесь стоят так, как стоят, из-за конкретных провалов, и трогать их
стоит зная о них.

**`SHOULDER_HALF_WIDTHS` были на единицу больше.** Руки висят *снаружи* плеч, так
что тяжёлое телосложение занимало 24 пикселя клетки из 32 — при голове в 12 и
паре ног в 9. Фигура читалась как широкая плоская доска с маленькой головой.
Плечи примерно в полтора раза шире головы — та пропорция, которая читается как
человек; заметно шире — и это читается как доспех сам по себе, без носителя.

**`ARM_DROP` раньше не было, то есть был ноль.** Руки, начинающиеся ровно на
линии плеч, дают силуэту одну прямую кромку во всю его ширину, а прямая кромка
такой длины — это доска: глазу негде найти плечо, руки перестают быть руками и
становятся краями груди. Двух строк спуска хватает, чтобы линия сломалась.

**`HEAD_HEIGHT` было 13.** Лишняя строка ничего не давала лицу и стоила
единственного, что читается как сустав: черепу, кончающемуся строкой ниже, шея
доставалась в одну строку, а одна строка чего угодно — не деталь.

**Раньше спрайт был 24×32 — ровно тайл в ширину и тайл в высоту, — и в коде
записано, что это была самая плохо выглядевшая вещь в игре.** Причин две, и
только одна из них про размер. При 32 строках и девятистрочной голове на торс
остаётся восемь строк, а восемь строк должны нести плечи, грудь, пояс и то, во
что персонаж одет: одежде физически негде быть чем-то кроме одного плоского
пятна цвета, поэтому каждый персонаж читался как цветная полоска с лицом сверху.
И фигура высотой ровно в тайл — это фигура высотой ровно с траву, в которой она
стоит, что убивает подсказку масштаба, говорящую «это человек в мире», а не «это
ещё один тайл».

Сейчас 32×48: тайл в ширину, полтора в высоту — пропорция, на которой жанр
остановился, — и торсу достаётся тринадцать строк, чего хватает на тунику с
поясом, воротник и затенённый бок.

Голова — четверть высоты фигуры. Это всё ещё героические, а не жизненные
пропорции, и это сознательно: анатомически верная голова на 48 строках выходит
шириной шесть пикселей, и лица в ней нет. При старых 32 строках голову
приходилось делать **третью** фигуры, чтобы лицо в неё влезло, — отсюда прежний
спрайт и читался как чиби, независимо от того, хотели этого или нет.

Голова, торс и ноги — 13, 12 и 14 строк. Ноги не короче торса — иначе фигура
читается как комод на колёсиках.

Тело — 22 пикселя в клетке 32: запас по ширине нужен под замах оружия и под
контур, которые иначе обрезались бы краем кадра. Рендерер ставит персонажа по
точке между ступнями (`FEET_ROW = 45`), а не по центру спрайта: симуляция
двигает именно эту точку, и любая другая привязка развела бы спрайт с его
хитбоксом.

Сбоку фигура **уже**: плечи на два пикселя, голова на один. Раньше она была
одинаковой ширины со всех сторон, и вид сбоку читался как вид спереди с
замазанным глазом. Человек в профиль заметно уже, чем в фас, и эта разница в
силуэте — большая часть того, по чему зритель понимает направление ещё до того,
как разглядит лицо.

### 8.4 Раскладка листа

Три направления × четыре позы, кадров на позу: `POSE_FRAMES = {IDLE: 2, WALK: 4, ATTACK: 3, HURT: 1}`.
Итого `FRAMES_PER_CHARACTER = 3 * 10 = 30` кадров.

Направлений три, а не четыре: `SIDE` рисуется один раз и отражается рендерером
(`facingFor` в `render/characters.ts`). Это стандартная практика, и она вдвое
сокращает и время печати, и место.

Персонажи **не лежат в атласе** — их вид зависит от пяти байт, и печать всех
сочетаний дала бы страницу размером с мир. Вместо этого на каждую внешность
запрашивается один лист: `GET /api/atelier/character-sheet.png?body=..&hair=..&palette=..&outfit=..&accent=..`,
и второй такой же с `normals=true`. Раскладка публикуется в `atlas.json` в поле
`character`, чтобы клиент не держал копию `POSE_FRAMES`:

```
row = facing * 4 + pose
столбцов = max(POSE_FRAMES) = 4, короткие позы оставляют хвост строки пустым
клетка = 32 × 48
```

Одним листом, а не двенадцатью полосками: двенадцать запросов на каждого
вошедшего в поле зрения игрока — слишком много круговых поездок. Полоска на
одну позу тоже есть (`/api/atelier/character.png?facing=..&pose=..`), её
использует титульный экран, где смысл именно в одной позе.

### 8.5 Порядок рисования и оснастка

```python
    _shadow(surface, bones.centre)      # эллипс на земле
    _far_arm(...)                       # дальняя рука
    _legs(...)
    _neck(...)                          # до торса, иначе воротник его не прикроет
    _torso(...)
    _near_arm(...)                      # ближняя рука после торса
    _head(...)
    ops.outline(surface, "shadow", level=0, alpha=225)
    ops.contact_shadow(surface, rows=2, amount=0.28)
```

Порядок — не вкусовщина. Рисовать не в том порядке — это то, из-за чего
процедурные персонажи выглядят как разнесённые схемы: у повёрнутой фигуры плечо
оказывается впереди подбородка.

`Rig` — смещения конечностей на кадр, `Skeleton` — абсолютные позиции всех
частей на кадр, посчитанные один раз и переданные вниз, чтобы голова знала, в
какой колонке шея, а руки — где на самом деле плечи. Покачивание корпуса уже
сложено внутрь: части выше бёдер двигаются с ним, ступни нет.

Ходьба: **вынос — косинус, подъём — синус**, и именно поэтому они разведены на
четверть цикла. Крайние точки выноса — это кадры опоры, где обе ступни на земле и
шаг раскрыт шире всего; нули выноса — кадры проноса, где ноги вместе, а идущая
поднята. Гнать и то и другое от одной волны, а тем более гнать один подъём,
означает сложить цикл в подёргивание, и это ровно то, чем цикл был: в первой
версии оснастки ноги только **укорачивались** на месте и никуда не выносились,
так что сбоку — с того угла, в котором персонаж проводит большую часть времени, —
фигура стояла и дёргалась. Руки идут в противомах, который есть в любой походке.
Покачивание корпуса — на **двойной** частоте, потому что бёдра поднимаются раз на
**шаг**, а не раз на цикл; перепутать это — самая заметная ошибка в рукодельном
цикле ходьбы.

Вынос и подъём — разные поля оснастки (`near_leg_swing` и `near_leg_lift`), и
разделены они потому, что читаются с разных углов. Сбоку походка — это почти
целиком вынос: зритель считывает шаг по расстоянию между лодыжками. В лоб этот же
вынос сокращён перспективой почти до нуля, и остаётся подъём. Отсюда же
`swing // 3` в отрисовке ног при виде спереди.

Удар: замах на первом кадре, удар на втором, возврат на третьем. Предвосхищение
— то, что превращает трёхкадровый замах в силу.

Важная деталь про то, как эти кадры проигрываются на клиенте: цикл ходьбы
привязан не к часам, а к **пройденному расстоянию** — один полный четырёхкадровый
цикл на два тайла (`animationFrame` в `render/characters.ts`). Поэтому ноги не
скользят по земле, но поэтому же кадр ходьбы, который выглядит хорошо только на
своей частоте, выглядеть хорошо не будет: скорость показа задаёт игрок. Остальные
позы идут от часов, на шести кадрах в секунду.

### 8.6 Как расширить или заменить рисованным артом

**Добавить позу.** Надо тронуть четыре места: `Pose` и `POSE_FRAMES` в
`character.py`, ветку в `_rig`, `Pose` в `frontend/src/render/characters.ts` и
`poseFor` в `frontend/src/render/props.ts`, который выбирает позу по байту
состояния и скорости. Раскладка листа поедет автоматически: и число строк, и
число столбцов выводятся из `POSE_FRAMES` и публикуются в индексе.

**Если новая поза не появляется, смотрите не на арт.** Позу выбирает `poseFor` по
байту состояния, и этот байт приходит с сервера: бит 0 — «жив», биты 1–3 — состояние.
Байт какое-то время не входил в пакет знакомства (`SERVER_SPAWN`), клиент подставлял
нуль, а нуль в бите 0 означает «мёртв» — и `poseFor` для всех до единого возвращала
`HURT`. В `HURT` один кадр, поэтому **в игре не двигался никто**: ни походка, ни бег,
ни удар, при полностью корректных листах спрайтов. Мораль для художника простая: если
поза не проигрывается, сначала посмотрите в диагностическом оверлее, какую позу
рендерер выбрал, и только потом ищите ошибку в кадрах. Арт здесь чаще всего ни при чём.

**Поменять пропорции.** Правьте только константы в блоке proportions. Всё
остальное читает их. Если после правки фигура рассыпалась, скорее всего
изменилось соотношение `HEAD_HEIGHT` и `SHOULDER_ROW`, а не конкретная функция.

**Заменить рисованным артом.** Здесь надо быть честным: **готового пути нет**.
Импортёр Aseprite (раздел 9) разбирает лист на кадры, теги и слайсы и возвращает
их вызывающему, но ничего никуда не записывает, а `CharacterCache` умеет
загружать лист **только** с `/api/atelier/character-sheet.png`. Чтобы поставить
нарисованного персонажа в игру, нужно одно из двух:

1. заставить `character_full_sheet` в `age/presentation/http_routes.py` отдавать
   ваш PNG вместо печати — быстрый путь, годится для одного персонажа;
2. добавить источник листов рядом с процедурным и ключ в `Appearance`, который
   его выбирает, — правильный путь, и это уже работа по коду.

Если пойдёте первым путём, соблюдайте контракт: клетка 32×48, строка
`facing * 4 + pose`, четыре столбца, кадров в позе как в `POSE_FRAMES`, ступни
на строке 45, и **вторая страница с нормалями** того же размера (клиент грузит
её тем же URL с `normals=true`). Без второй страницы персонаж получит плоскую
нормаль и будет освещён ровно — не сломается, но потеряет весь объём.

Тесты на персонажа есть, но их немного и они узкие: раздел `--- characters ---`
в `tests/test_age_atelier.py` утверждает семь свойств — что ступни стоят на строке
привязки, что кадры ходьбы не совпадают друг с другом, что сбоку лодыжки
расходятся хотя бы на четыре пикселя за цикл, что вид сбоку уже вида в лоб, что
акцент и штаны никогда не попадают в рампу одежды, и что в листе ровно столько
кадров, сколько ждёт нарезка. Все семь написаны по следам конкретных поломок, и
все семь ловят провалы силуэта и оснастки. Ни один из них не судит о том, красиво
ли получилось, — это по-прежнему `probe_character.py` и ваши глаза.

## 9. Импорт из внешних редакторов

Процедурные рецепты хорошо делают текстуру и совсем не делают замысел.
Бесшовный гравий — это пять строк рецепта; городская площадь, которая
чувствуется местом, плотностями разброса не описывается. Поэтому у конвейера два
входа.

Оба импортёра **конвертируют и докладывают**. Ни один не пишет в живой мир:
загрузка, применяющая себя сама, была бы способом перезаписать всё, что
построили игроки, из файла и без ревью. Оба проверяют форму всего, что читают,
потому что оба принимают файл из браузера, и любой некорректный файл возвращается
как 400 с причиной, а не как стек.

### 9.1 LDtk

`age/atelier/importers.py`, `load_ldtk`. Разбираются два слоя, по точным именам:

| Слой LDtk | Что с ним делают |
| --- | --- |
| `Terrain` | `IntGrid` или обычный слой тайлов → массив тайлов |
| `Props` | сущности → размещения пропсов |

Всё остальное в проекте игнорируется, так что вспомогательные слои можно
держать.

**Самое важное: тайлсет не нужен.** Красите классы рельефа как **IntGrid**, и
числа *и есть* идентификаторы тайлов. Одна поправка на единицу: ноль в LDtk
означает «пусто», а не тайл 0, поэтому импортёр берёт `value - 1`. То есть
значение IntGrid **1** даёт `BARE_GROUND` (0), **2** даёт `GRASS`, и так далее.
Голую землю надо красить явно — то же правило, что у самого LDtk.

Если слой обычный тайловый, а не IntGrid, читается `gridTiles`, и идентификатор
берётся из поля `t`, необязательно через таблицу `tile_mapping`.

Идентификатор из диапазона за пределами `Tile` не роняет импорт, а
превращается в голую землю. Ошибка становится видна на карте, а голая земля
отрастает, так что она не навсегда.

**Пропсы: имя сущности — это ключ рецепта.** Сущность LDtk с именем `lantern`
ставит рецепт `lantern`. В этом вся интеграция, никакой таблицы соответствий
поддерживать не надо. Читается ещё пользовательское поле `flipX` (булево).
Координаты возвращаются в тайлах, дробные (`px / grid_size`).

Что нужно от экспорта:

- **Один файл JSON, а не «Save as separate level files».** Подсказка в
  интерфейсе импортёра говорит об этом прямым текстом; при раздельном
  сохранении в `.ldtk` не будет `levels[].layerInstances`, и импорт вернёт «not
  an LDtk project».
- **Размер сетки 32.** Берётся из `defaultGridSize`, при отсутствии или нуле —
  32. Ширина и высота уровня считаются из `pxWid` и `pxHei`, делённых на сетку.
- **Имена слоёв ровно `Terrain` и `Props`**, с учётом регистра.

Результат: `ImportedLevel` с `tiles` (индекс внутри уровня → тайл) и `props`.
Метод `chunk_overlays()` режет уровень на наложения по чанкам,
`{(chunk_x, chunk_y): {tile_index: tile}}` с индексами, локальными для чанка, —
ровно та форма, которую принимает `World.apply_overlay`. Уровень крупнее одного
чанка (32×32 тайла) — нормальный случай для хаба, поэтому нарезка сделана в
импортёре.

Честные оговорки:

- **Применить результат нечем.** `World.apply_overlay` существует, эндпойнт
  `POST /api/atelier/import/ldtk` возвращает готовые наложения, но кода, который
  берёт одно и передаёт другому, нет. Пока это ручная работа или скрипт, который
  надо написать.
- **Пропсы из LDtk никуда не идут.** Клиент выводит декор сам, в `decor.ts`
  (раздел 3.3), и не читает ни `props` из импорта, ни `decor` из индекса атласа.
- **Панель результата в браузере не отрисует то, что вернул сервер.**
  `Importers.tsx` ждёт `chunks[].key` строкой и `chunks[].tiles` числом, а сервер
  отдаёт `chunkX`, `chunkY` и словарь тайлов, — то есть панель пытается вывести
  объект как текст, чего React не делает. Сама конвертация при этом работает:
  ответ эндпойнта корректен, сломано его отображение. До починки смотрите ответ в
  инструментах разработчика или дёргайте эндпойнт скриптом.

### 9.2 Aseprite

`load_aseprite`. Читается экспорт `json-array`:

```bash
aseprite -b sprite.aseprite --sheet sheet.png --format json-array --list-tags --list-slices --data sheet.json
```

- **Только `json-array`.** Хеш-формат **отклоняется** с явным сообщением, а не
  поддерживается: порядок кадров в нём приходится восстанавливать из ключей
  хеша, то есть разбирать тот шаблон имени файла, который автор случайно
  выбрал. Это не контракт, на который стоит опираться. В массиве порядок и есть
  порядок кадров.
- **Теги** читаются из `meta.frameTags`: имя, `from`, `to`, `direction`. Это
  прямо ложится на модель «поза и кадр», которой рендерер уже пользуется для
  сгенерированных персонажей.
- **Слайсы важнее, чем кажется.** Читается `meta.slices`, и слайс с именем
  **`anchor`** — это способ художника сказать «ступни здесь». `pivot`
  вычисляется как `(x + w // 2, y + h)`, то есть середина по горизонтали и низ
  по вертикали. Рендереру это необходимо: высокий спрайт, привязанный по центру,
  ставит на тайл не сапоги персонажа, а его пояс.
- Из `meta.size` берутся размеры листа, из `meta.image` — имя картинки. Длина
  каждого кадра — `duration` в миллисекундах, по умолчанию 100.

В экспорте через интерфейс это галочки «Meta: Tags» и «Meta: Slices» в диалоге
Export Sprite Sheet; без них разделы `frameTags` и `slices` в JSON не попадут, и
импортёр честно вернёт лист без тегов и без якоря.

Честная оговорка: как и с LDtk, дальше результата дело не идёт. Импортёр
возвращает описание листа; ни рендерер, ни атлас нарисованный PNG не подхватят
(раздел 8.6).

## 10. Браузерный редактор

`/age/atelier`. Отдельная точка входа в том же бандле, чтобы игра не тащила с
собой редактор. Если клиент не собран, эндпойнт честно отвечает 503 с текстом
«run npm install && npm run build».

### 10.1 Что он умеет

- **Список рецептов** с фильтром, с размером и числом кадров у каждого, и с
  меткой `unused` у тех, на которые не ссылается ни один тайл и ни один ключ
  декора. Метка полезная: несвязанный рецепт — это либо декор, либо забытая
  привязка, и больше это нигде не видно.
- **Список шагов**: добавить (вставляется **после** выделенного, а не в конец —
  порядок в рецепте это всё, и добавить шаг в конец, когда хотел сюда, самая
  частая ошибка), передвинуть вверх-вниз, удалить. Рядом с каждым шагом
  показывается образец цвета: его рампа на его уровне.
- **Параметры шага** типизированными контролами: рампа выпадающим списком из
  каталога, уровень ползунком 0…4, прямоугольник четырьмя числами, сид с
  кнопкой «Roll», остальное ползунками с разумными границами.
- **Живая печать** — `POST /api/atelier/bake` с задержкой 220 мс после последней
  правки. Это настоящий серверный бейкер, а не пересказ: была версия, которая
  печатала локально на TypeScript ради отзывчивости, и она разошлась с Python в
  первый же день. Превью, расходящееся с экспортом, — единственная поломка,
  которой у художественного инструмента быть не должно.
- **Переключатель нормалей**, масштаб 1…8, сид, число кадров 1…8.
- **Экспорт PNG** (полоска всех кадров, или её карта нормалей) и **Copy JSON**.
- **Вкладка Atlas**: обе страницы целиком, масштаб 1…4, скачивание. Отдельная
  вкладка нужна потому, что проблемы упаковки не видны в превью одного рецепта:
  спрайт, вылезший из своей клетки, или карта нормалей, не совпадающая с
  цветовым близнецом, видны только здесь.
- **Вкладка Import** для LDtk и Aseprite, с приёмом файла перетаскиванием.

### 10.2 Что он не умеет

- **Не сохраняет.** Это решение, а не пробел: рецепт — исходный код, он живёт в
  `age/atelier/recipes.py` и проходит ревью, как всё остальное. Редактор,
  умеющий писать прямо в работающий мир, был бы способом менять арт так, что
  никто не увидит диффа. Обратный путь — кнопка **Copy JSON**.
- **Не создаёт рецепт с нуля.** Кнопки «новый» нет. Практика: выберите ближайший
  существующий, правьте его, копируйте JSON.
- **Не рисует по пикселям.** Инструмента кисти нет и не предполагается.
- **Не отменяет.** Undo нет, есть только **Revert** к состоянию из каталога.
- **Не показывает ground-тайлы.** Это баг, и о нём надо знать, потому что он
  выглядит как пустой редактор. `RecipeList` группирует по `kind === 'ground'`
  и `kind === 'prop'`, а Python отдаёт ground-рецептам `kind: "tile"`
  (см. `_ground` в `recipes.py`). В результате все 12 ковров не попадают ни в
  одну группу и в списке не видны, а превью «Tiled» 3×3 — единственный способ
  увидеть шов — не показывается по той же причине. Пока это не исправлено, шов
  проверяется через `probe_atelier.py` и файлы `tile-<name>.png`.

### 10.3 Расхождения между редактором и бейкером

Редактор описывает операции у себя, в `frontend/src/atelier/types.ts`, а не
получает описание с сервера. Это осмысленно (можно работать по кешированному
каталогу, добавление ползунка не требует правки сервера), но несколько мест
разъехались:

| В редакторе | В бейкере | Следствие |
| --- | --- | --- |
| `op: 'mirror_horizontal'` | `op == "mirror"` | шаг «Mirror», добавленный в редакторе, не делает ничего |
| у `ripple` поле `thickness` | читается `band` | ползунок «Crest height» ни на что не влияет |
| у `ripple` нет поля `rect` | `rect` читается | ряби нельзя задать область — только весь холст |
| у `flicker` поле `Seed` | сид не читается | ползунок ни на что не влияет |
| `shift` и `glow` отсутствуют | обе работают | две из шести анимаций в редакторе недоступны |
| нет полей `material`, `onlyOnOpaque`, `litFromLeft` | все три читаются | эти параметры правятся только в коде |

Практический вывод: редактор хорош, чтобы набросать форму и покрутить цвета, но
финальный рецепт всё равно доводится в `recipes.py`. Для `mirror` пишите ключ
вручную (`{"op": "mirror"}`), для `ripple` — `band` и `rect`, для `shift` и
`glow` — весь шаг целиком.

### 10.4 Рабочий порядок для рецепта руками

1. Открыть `/age/atelier`, найти ближайший по смыслу рецепт.
2. Править шаги, глядя на превью. Держите включённым переключатель нормалей
   хотя бы часть времени: половина ошибок по высоте видна только там.
3. Погонять сид кнопкой «Next»: рецепт, который хорошо выглядит на одном сиде и
   плохо на трёх соседних, ещё не готов.
4. **Copy JSON**.
5. Вставить в `age/atelier/recipes.py` как вызов `_ground(...)` или `_prop(...)`.
   JSON из редактора несёт `key`, `kind`, `width`, `height`, `frames`,
   `seamless`, `anchorY`, `label` и `steps` — из них в вызов помощника идут
   только `key`, высота, шаги, `frames`, `anchor_y` и `label`; остальное
   помощник задаёт сам.
6. Перезапустить сервер, прогнать `probe_atelier.py`, посмотреть контрольные
   листы, прогнать `pytest tests/test_age_atelier.py`.

## 11. Хорошие практики пиксель-арта для этого проекта

Всё ниже — не общая теория, а уроки, записанные в комментариях этого кода
после того, как что-то пошло не так. Они стоят дорого и потому приведены с
конкретикой.

### 11.1 Силуэт важнее затенения

**Утёс, который читался как радиатор.** У `cliff` было две предыдущие версии, и
обе провалились поучительно. Первая дизерила прямоугольник во всю ширину от
оттенка 2 к 0 и рисовала расщелины тонкими тёмными линиями: на таком размере
пиксельный контраст уничтожает форму, и получалась рябь телевизора. Вторая
заменила текстуру чистыми плоскостями — светлая горизонтальная шапка над тёмным
фасадом с двумя вертикальными расщелинами — и читалась как радиатор, потому что
прямоугольник со светлой полосой сверху и тёмными полосами вниз **и есть**
радиатор, как бы ни называлась рампа.

Не хватало обеим одного: неровного контура. Камень узнаётся по силуэту задолго
до того, как разглядят его затенение. Поэтому масса выращена из блобов с
`wobble`, и прямой оставлена только юбка там, где утёс встречается с землёй.

**Фонарь, который читался как ручное зеркало.** Первая версия рисовала три
концентрических вихляющих круга на палке. Светлое кольцо вокруг светлого
центра — это линза. Фонарь — сделанный предмет, и его прямые кромки составляют
половину того, по чему его узнают, поэтому итоговый рецепт собран из
прямоугольников: колпак, стекло, основание и две стойки, причём колпак и
основание на пиксель шире стекла, чтобы нависать над ним. И шпиль сверху —
именно он говорит, где у предмета верх.

**Фонтан, который читался как флакон зелья с крыльями стрекозы.** Самый
поучительный провал в наборе, и в нём сразу два разных урока. Первая версия
собрала фонтан из круглых блобов — большой на чашу, меньший сверху на верхнюю
чашу — и диагональных линий на падающую воду.

Первый урок: **чаша — это широкий низкий эллипс, а круг той же площади читается
как сосуд**, потому что сосуды примерно так же высоки, как широки, а водоёмы нет.
Второй: **всё, что выходит за силуэт, становится частью силуэта.** Тонкие светлые
диагонали снаружи основной массы прилипли к контуру и прочлись как крылья, а не
как вода. Итоговый рецепт набирает эллипс стопкой прямоугольников убывающей
ширины — так эллипс и рисуют на таком размере, — и ни одна деталь не пересекает
контур: струя целиком лежит в пределах ширины чаши под ней.

**Крышка бочки, которая читалась как колесо.** Круглый блоб на крышку выпирал за
клёпки и выглядел колесом, приставленным к ящику: крышка, видимая под этим углом,
— низкий эллипс, никогда не диск. Собрана она, соответственно, тоже строками. И
дизеринг у бочки идёт **по горизонтали**, а не по вертикали: круглость бочки — в
поперечном направлении.

**Мешки — наоборот.** У `sacks` `wobble` 0.38–0.42 и купол включён именно потому,
что весь смысл мешка в том, что у него нигде нет прямых кромок.

Общее правило: **органика — блобами с `wobble`, сделанные предметы —
прямоугольниками и `column`**. Перепутать — и камень выглядит штампованным, а
фонарь оплывшим.

### 11.2 Шум — не текстура

**Гравий.** Пиксельный шум любой плотности читается как рябь телевизора.
Рассыпанный камень читается как камень потому, что он лежит **комьями** по
два-три пикселя с тёмными промежутками. Отсюда `_pebbles`: четырнадцать мелких
блобов в хешированных позициях вместо `scatter` с высокой плотностью.

**Песок.** Два прохода `scatter` со смещёнными сидами читаются как рябь от
ветра. Один проход читается как шум. Разница — в одной строке рецепта.

**Цветы — по одному пикселю.** В `planter` цветы сделаны `scatter`, а не блобами:
пятно цвета `cloth` размером с настоящий цветок читается как плод, а один пиксель
читается как цветок, потому что на этом масштабе цветок — это и есть один
пиксель. Два прохода — красный и золотой, разной плотности.

**Блоб не шумит по пикселям.** `blob` берёт восемь радиальных контрольных точек
и плавно интерполирует между ними. Пиксельный шум по радиусу лохматил бы силуэт
вместо того, чтобы формовать его.

**Дизеринг упорядоченный.** Диффузия ошибки даёт крупу, которая ползёт при
движении спрайта.

### 11.3 Плоскостей должно быть больше одной

**Ящик.** Первая версия была прямоугольником. Ящиком он стал, когда появилась
вторая плоскость другой яркости — крышка сверху. Без второй плоскости никакое
затенение не спасает. А угловые стяжки и косая распорка — то, что говорит
«собрано», а не «выточено».

**Дерево.** Один блоб кроны читается как леденец на палочке. В `tree` три доли
на разных уровнях (1, 2, 3) и ствол **первым**, чтобы крона его перекрыла.

**Стена.** Двух соседних пикселей противоположной яркости достаточно, чтобы
одна заливка распалась на отдельные доски. И горизонтальная полоса сверху —
самый дешёвый способ сказать «это стена, и вы смотрите на неё сбоку».

**Одна деталь, по которой предмет узнают.** У половины хабового набора есть
ровно один элемент, без которого он превращается в другой предмет, и в рецептах
это выписано:

- у прилавка — **полосы на навесе**. Простой навес на ножках — это сарайчик;
  чередующиеся полосы ткани — единственное, что говорит «рынок» на шестнадцати
  пикселях. Плюс фестончатый подзор снизу, который читается как висящая ткань.
- у колодца — **кровля**. Без неё, на этом размере, он неотличим от ящика с
  землёй.
- у вывески — **кронштейн**, та самая «Г», из-за которой щит читается подвешенным,
  а не приколоченным заподлицо, и два пикселя цепи.
- у ящика — **крышка** как вторая плоскость другой яркости.
- у бочки — **два обруча**.

**Товар на прилавке: три комка разной высоты, и ни одной пары одной рампы.**
Одинаковые комки читаются как орнамент, а не как товар.

**Знак на вывеске нарочно нечитаемый.** Настоящая литера должна была бы что-то
означать, а тогда все лавки в городе говорили бы одно и то же.

**Утёс, ещё раз.** Основание у него на оттенке 3, а не 1. При 1 промежутки
между освещёнными фасетами были почти чёрными, и результат читался как бледные
камни, плавающие в дёгте, а не как одно каменное тело с по-разному повёрнутыми
плоскостями.

**Одна асимметричная трещина читается как геология. Две параллельные — как
машина.**

### 11.4 Порядок шагов — часть рецепта

**Доски стены.** У ранней версии швы рисовались первыми, а потом фасад
дизерился поверх них: швы закрасило, и остался плоский крапчатый щит, который
читался как дощатый пол сверху. Градиент должен лечь **до** линий, описывающих
доски.

**Костёр.** Камни, потом брёвна, потом пламя — пламя последним, чтобы проход
эрозии тронул только огонь: камни и брёвна лежат ниже `aboveRow` и остаются на
месте, как и должны.

**Контур.** `outline` собирает кромку сначала и записывает потом, чтобы новые
пиксели кромки не порождали следующие. Это внутри операции, но следствие
наружу: контур почти всегда идёт **перед** контактной тенью и перед `sway`.

### 11.5 Цвет

- Сдвиг тона по рампе — самая большая разница между плоским и написанным.
- Насыщенность растёт в тень, а не падает.
- Лестница светлоты нелинейна; линейная выбивала блики в белый и сплющивала
  весь тайлсет в глянец.
- Тёплым тонам разворачиваться некуда: при сдвиге 0.055 загар `bc8a64` в тени
  становился `a7463b` — на лице это травма.
- Зрачок берёт **нулевой** оттенок `shadow`, а не первый: даже на двух пикселях
  цвет не может быть приблизительно верным, средний тон читается как румянец.

### 11.6 Персонаж

Всё это записано в `character.py`, и всё это следствия провалов ранних версий,
одна из которых читалась как марионетка, другая — как штабель блоков, третья —
как цветная полоска с лицом сверху.

- **Размер решает больше, чем рисунок.** Переход с 24×32 на 32×48 сделал для
  персонажа больше, чем любая правка деталей: до него у торса просто не было
  строк, чтобы одежда была чем-то кроме одного пятна цвета (раздел 8.3).
- Шея обязательна и рисуется **до** торса. После торса она превращалась в
  светлую полосу кожи по ключицам и читалась как красный воротник. Ширина шесть
  пикселей: при двух это галстук-бабочка. Со спины шеи нет — там волосы доходят
  до затылка.
- Углы челюсти скругляются стиранием, и на голове шириной 12 пикселей одного
  пикселя на угол **не видно** — скос идёт на две строки. Это разница между
  головой и костяшкой домино. Виски скругляются сверху тем же приёмом.
- Одна освещённая строка по лбу, с отступом внутрь. Две во всю ширину читаются
  как головная повязка, что хуже, чем вообще без моделировки.
- Глаз — два пикселя, и **прямо на нём сверху** строка ресниц цветом волос. Бровь
  была отдельной деталью, на две строки выше, с кожей между: на голове в 12
  пикселей это две тёмные горизонтальные чёрточки схожего веса одна над другой, и
  глаз не собирает их в лицо — он читает их как четыре глаза. Что хуже той
  проблемы, ради которой бровь добавляли (лицо с голыми глазами выглядит
  испуганным). Сросшись, ресница и зрачок дают один двухстрочный глаз с
  очерченным верхним веком, и веко делает ту же работу, что делала бровь. Цвет
  зрачка — самый тёмный оттенок `shadow`: средний тон на двух пикселях читается
  как румянец.
- Рот — **один** пиксель. Два читаются как гримаса: горизонтальная метка в два
  пикселя на этом масштабе шириной с глаз и группируется с глазами, а не с
  подбородком.
- Сбоку виден **только ближний глаз**. Два глаза в профиль превращают вид сбоку
  в плоскую маску, повёрнутую набок.
- Волосы: венец в две строки, не в четыре. Прикрыв половину черепа, вы не
  оставите лица, а лицо — единственная причина рисовать голову на таком
  размере. Верхняя строка сужена на два пикселя с каждой стороны, чтобы череп
  был куполом: **плоский верх копны волос — самый частый признак процедурного
  персонажа**.
- Ноги четыре пикселя шириной. При двух это болотная птица. Сбоку ноги
  перекрываются, а не расходятся, — иначе фигура кривоногая со всех сторон.
  Поднятая нога **короче**, а не выше: ступня уходит с земли, колено сгибается.
- Штаны не берут нижние оттенки рампы: там они сходились по яркости с обводящим их
  контуром, и обе ноги вместе с промежутком между ними сливались в одну тёмную
  трапецию — цикл ходьбы пропадал. Ноги должны быть тёмными относительно туники и
  светлыми относительно контура. Ближняя нога — оттенок 3 всегда; дальняя — 0
  сбоку, где она действительно в тени ближней, и 2 в лоб, где обе освещены
  одинаково и та же разница читалась бы как разные штанины, а не как глубина.
- Спереди между ногами нужен **свой** контур: они смыкаются без промежутка, и две
  колонки одной рампы в пару оттенков друг от друга читаются как одна масса. Тот
  же приём, что у рукава, и по той же причине.
- Рукав отделён от груди тёмной кромкой в один пиксель **со стороны торса**. Одного
  оттенка разницы не хватило: рука прилегает к груди без зазора, и глаз читает два
  соседних оттенка одной рампы как одну освещённую поверхность. Кромку надо
  ставить со стороны тела — на внешнем краю она потрачена впустую, там уже есть
  контур силуэта.
- Воротник: одна строка одежды на нижнем оттенке там, где туника встречает шею.
  Без неё затенение шеи переходит прямо в затенение груди, и стык читается как
  смазанность, а не как «одежда кончилась, началось тело».
- Шея сама набрана двумя оттенками, светлым и тёмным. Плоский прямоугольник одного
  тона между челюстью и воротом читается как дырка в спрайте; два оттенка делают
  его цилиндром, а цилиндр под головой — это шея, и ничего больше говорить не
  надо.
- Пояс — **две** строки: светлая над тёмной. Одна строка среднего тона — это один
  оттенок на фоне другого, и он теряется на общем плане, а светлая полоса над
  затенённой имеет толщину.
- Обувь — самый тёмный элемент фигуры, из чего бы она ни была: это часть в
  собственной тени земли.
- Рукав — другой оттенок **той же** рампы, что и грудь: светлее у ближней руки,
  темнее у дальней. Рука шириной три пикселя точно того же цвета, что грудь, к
  которой она прилегает, просто отсутствует.
- Между рукавом и кистью — **манжета** в одну строку. Без неё предплечье и кисть
  читаются как одна сужающаяся палка.
- Торс — два блока, а не один: плечи, потом более узкая талия. Один
  прямоугольник шириной с плечи читается как ящик, и никакое затенение это не
  лечит. Пояс даёт силуэту талию.
- Покачивание корпуса — на двойной частоте относительно цикла: бёдра
  поднимаются раз на **шаг**, а не раз на полный цикл.
- Амплитуды в оснастке — в пикселях, поэтому они выросли вместе со спрайтом. Шаг
  в три пикселя на фигуре в 32 строки был третью длины ноги и читался как
  строевой марш; на 48 строках те же три пикселя — обычный шаг.
- Дыхание в покое — **один** пиксель. Два на стоящей фигуре читаются как
  одышка.

### 11.7 Композиция важнее количества

Урок не про пиксели, а про расстановку, и он свежий: он записан в
`render/decor.ts` после того, как первая версия площади провалилась.

Первая версия расставляла хаб арифметикой: костёр в центре, четыре фонаря по
углам, фонарь на каждом перекрёстке. Сто с лишним тайлов мощения и семь предметов
на них. Формально — освещённый город; читалось — пустое поле с фонарными столбами.
Из этого следуют три конкретных правила, по которым собран нынешний хаб:

- **Расставляйте от главного предмета.** Фонтан — фокус площади, и всё остальное
  расположено относительно него: лавки по диагоналям, лицом внутрь; ящики с
  растениями смягчают четыре прямых подхода; знамёна в устьях улиц. На осях через
  центр не стоит ничего, кроме знамён, потому что четыре устья улиц — это то,
  откуда игрок входит, и перекрывать оттуда вид на фонтан значит потратить его
  впустую.
- **Неровные промежутки.** Прилавки стоят с разными интервалами: расставленные
  ровно, они читаются как колоннада. И они отодвинуты от улицы, а товар вынесен
  перед ними — ряд прилавков вплотную к кромке мостовой читается как забор.
- **Предмет получает смысл от места.** Костёр сначала стоял на площади. Огонь
  посреди парадной мощёной площади — это лагерь, а не город. Тот же спрайт,
  перенесённый на хозяйственный двор за площадью, читается как место, где что-то
  варят.

Правилом осталось только уличное освещение — сетка улиц генерируется, значит и
лампы на ней должны, — и то с оговоркой: шаг между фонарями пришлось уменьшить
с двенадцати тайлов до шести, потому что при двенадцати между ними оставались
длинные тёмные провалы.

### 11.8 Смотрите на арт глазами

Ни одно из перечисленного не видно в ревью кода, и всё видно на одной картинке.
Пробы арта — `probe_atelier.py` и `probe_character.py` — это то, чем осматривали
пропсы, и они поймали утёс-радиатор, фонарь-зеркало, фонтан с крыльями
стрекозы, крышку бочки в виде колеса и костёр, который вообще не анимировался.
Печать в файлы занимает секунды и не требует сервера. Делайте это после каждой
правки рецепта.

Тесты ловят другой класс ошибок — те, что видны в цифрах, а не глазами. Вывеску,
у которой все четыре кадра испеклись побайтно одинаковыми, поймал
`test_animated_recipes_differ_between_frames`, а не осмотр: одинаковые кадры на
контрольном листе выглядят как нормальная вывеска. Поэтому прогоняйте и то, и
другое.

И проверяйте бесшовность на поле, а не на клетке. `tile-<name>.png` — это тайл,
повторённый 4×4; шов виден там и не виден нигде больше.

## 12. Что делать дальше

Список по убыванию отношения «отдача на час работы». Первые четыре пункта — про
то, чтобы существующий конвейер заработал целиком; остальные — про наполнение.

**1. Автотайлинг по каналу `material`.** Холст его пишет, ground-рецепты
заполняют осмысленными индексами (1 земля, 2 трава, 3 песок, 4 гравий, 5 грунт,
6 камень, 7 доски, 8 снег, 9 пепел, 10 вода), и **ни одна строка кода его не
читает**. Сейчас трава встречается с песком жёстким краем. Переходные тайлы по
этому индексу — самая большая визуальная отдача из всего, что осталось, и это
же записано в [roadmap.md](roadmap.md).

**2. Сохранение рецептов из редактора.** Редактор печёт и экспортирует, но
правка живёт в браузере, и её надо вручную переносить в `recipes.py`. Запись
рецептов на диск замыкает петлю и превращает редактор в настоящий инструмент.

**3. Расстановка декора данными, а не кодом.** Площадь хаба обставлена — все
двенадцать декоративных пропсов расставлены таблицами `PLAZA`, `MARKET` и `YARD` в
`render/decor.ts`, — но это **код клиента**, а не контент: каждое новое место
требует правки TypeScript и пересборки, и за пределами хаба расставить нельзя
ничего. Импортёр LDtk уже отдаёт размещения пропсов в готовом виде,
`World.apply_overlay` уже принимает наложения рельефа, но связать одно с другим
нечем: клиент не читает ни `props` из импорта, ни `decor` из индекса атласа. Это
единственный пункт, который открывает возможность делать **места**, а не
текстуры, — второй город, лагерь, руины.

**4. Починить расхождения редактора и бейкера.** `kind: "tile"` против
`'ground'` (из-за чего в редакторе не видно ни одного ground-тайла и не работает
превью бесшовности), `mirror_horizontal` против `mirror`, `thickness` против
`band` у `ripple`, отсутствие `shift` и `glow` в списке операций, игнорируемый
`seed` у `flicker`, и формы ответов импортёров, которых панель результата не
понимает (у LDtk она пытается вывести объект как текст, чего React не умеет).
Каждое — правка на несколько строк, и все они сейчас выглядят как «инструмент
сломан».

**5. Разнообразие внутри биома.** Дерево одно, куст один, камень один. Лес — это
двадцать копий одного дерева в сетке. Дешёвый ход: три-четыре варианта рецепта
на один тайл и выбор по хешу тайла — но выбирать вариант сейчас нечем, привязка
`TILE_PROP` — одна на тайл. Это небольшая правка привязок плюс правка
`propFor` в `render/atlas.ts`.

**6. Покрытие биомов.** `HEATH` и `ASHLAND` переиспользуют гравий и пепел,
`DESERT` — песок и кактус, и это всё. Рампы `dry_grass` и `dead_leaf` стоят
неиспользованными ровно под эти биомы. Один ковёр и два пропса на биом — и мир
перестанет быть одинаковым от края до края.

**7. Соблюдать `TILE_ANIMATION`.** Объявленная частота кадров игнорируется,
всё анимируется от одного счётчика на 6 кадрах в секунду. Пока это так, любая
анимация должна рассчитываться на 6 fps, и два костра рядом идут в такт.

**8. Персонажи.** Нарисованный вручную персонаж не имеет пути в рендерер (раздел
8.6). Из снаряжения рисуется только клинок в позе удара, и он не зависит ни от
класса, ни от того, что надето, — то есть экипировка меняет числа и не меняет
силуэт. Это самый заметный оставшийся разрыв между механикой и артом.

**9. Звук.** Его нет совсем, и канал `material` — уже готовый ключ для шагов.

**10. Эффекты способностей на клиенте.** Бой разрешается правильно и рисуется
минимально. Следы снарядов, вспышки попаданий и реакции — чистая презентация,
которая ничего не стоит на проводе.

**11. Перекраска биомов и сезоны.** Технически это одна строка на рампу:
`RAMPS` — словарь, собранный из `BASE_COLOURS` при импорте модуля. Но атлас
печётся один раз за жизнь процесса, и второй набор рамп потребовал бы второй
атлас и способ выбирать между ними в индексе. Красивая возможность, за которой
стоит реальная работа, — не обманывайтесь простотой палитры.

Наконец, одна деталь про документацию, чтобы не искать её впустую. В докстринге
`age/atelier/palette.py` сказано, что генератор рамп продублирован в
`frontend/src/atelier/palette.ts`; в `art-pipeline.md` и в комментарии к
`ATLAS_SIZE_PX` в `age/domain/constants.py` — что клиент печёт атлас сам при
загрузке. Ни того, ни другого больше нет: TypeScript-бейкер был и был убран,
потому что разошёлся с Python за день (об этом прямо написано в
`frontend/src/atelier/Inspector.tsx`). Клиент забирает готовые страницы с
сервера. Единственный бейкер — на Python.
