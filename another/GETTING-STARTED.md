# Первый запуск: от админки до трафика

Этот документ отвечает на один вопрос: «всё задеплоено, я одновременно
администратор и пользователь — что мне делать, чтобы через это пошёл мой
трафик». Про сам деплой (Space, воркер, секреты) — [DEPLOY.md](DEPLOY.md).

Здесь описано только то, что проверено на работающем коде. Там, где что-то не
работает или работает частично, это сказано прямо, а не спрятано.

---

## Часть 1. Что где живёт

Система состоит из трёх частей, и их роли не совпадают с тем, что можно
предположить по названиям.

| Часть | Где | За что отвечает |
| --- | --- | --- |
| Control plane | Hugging Face Space, префикс `/another` | База (MongoDB), админка, внутренний API для воркера. Трафик через себя **не** пропускает. |
| Edge | Cloudflare Worker | И авторизация (`/enroll`, `/nonce`, `/auth`), и **сам VPN-трафик** (`/proxy`). |
| Клиент | ваша машина | Go-бинарник `core/cmd/desktop`. Локальный HTTP API на `127.0.0.1:47821`. |

Главное, что стоит уяснить: **точка выхода в интернет — это сам воркер.**
Он не проксирует трафик на какой-то отдельный сервер, а открывает исходящие
TCP-соединения сам, через `connect()` из `cloudflare:sockets`
(`edge/src/handlers/proxy.ts`). Поэтому для трафика **не нужен** ни VPS, ни
Go-сайдкары `xhttp-origin` / `reality-origin` — они относятся к Tier2 и к
транспортам, которые сейчас не развёрнуты.

Flutter-приложение в `app/` для этого не нужно: код есть, но платформенные
папки не сгенерированы и SDK не настроен. Всё, что оно делает, — вызывает тот
же локальный API Go-ядра, что и мы вручную.

## Часть 2. Чего ожидать: что работает, а что нет

Прочитайте эту таблицу до того, как начнёте, чтобы потом не искать
несуществующую ошибку.

| Что | Состояние |
| --- | --- |
| TCP-трафик (HTTP, HTTPS, SSH, почта) | Работает |
| DNS | Работает. Клиент сам превращает UDP-запрос на порт 53 в DNS-over-TCP, потому что воркер не умеет UDP (`core/internal/adapters/netstack/engine.go`) |
| Остальной UDP: QUIC/HTTP3, WireGuard внутри туннеля, игры, голос | **Не работает.** Клиент отправляет такие потоки как TCP (все транспорты жёстко пишут `CommandTCP`), воркер тоже всегда открывает TCP. Браузеры при неудаче QUIC откатываются на TCP, так что веб от этого не страдает, а вот звонки и игры — да |
| Сайты за Cloudflare | **Может не открываться.** Воркерам запрещены исходящие TCP к собственным диапазонам Cloudflare (комментарий в `proxy.ts:19-21`). Насколько это мешает — проверяется только практикой |
| ICMP, то есть `ping` через туннель | Не работает, пакеты отбрасываются осознанно (`engine.go`) |
| Учёт трафика | Считается, но записывается одной суммой в конце соединения, а не в реальном времени |
| Квота и бан | Проверяются в момент `/auth`, то есть при подключении. Уже открытая сессия по превышению квоты не рвётся |

### Почему нельзя просто взять v2rayN, Nekoray, sing-box или Hiddify

Формат VLESS здесь стандартный, но обычный клиент всё равно не подключится, и
дело не в мелочи, которую можно донастроить. Перед тем как пустить трафик,
воркер требует пройти процедуру, которой в стандартных клиентах нет:

1. `GET /nonce` — получить одноразовое случайное значение.
2. Подписать его ключом Ed25519 устройства и отправить `POST /auth`.
3. Получить `session_token` и `vless_user_id`.
4. Открыть WebSocket на `/proxy` с заголовком `Authorization: Bearer <session_token>`
   (`proxy.ts:28-36`) — без него ответ `401`.
5. В VLESS-заголовке предъявить именно тот `vless_user_id`, который выдан этой
   сессии; иначе соединение закрывается с кодом `1008` (`proxy.ts:87-93`).

Сам `vless_user_id` выдаётся только после `/enroll` с публичным ключом
устройства. Ссылки вида `vless://uuid@host:443` тут не существует в принципе.
Поэтому клиент — только собственное Go-ядро.

## Часть 3. Пошагово

Дальше `$WORKER` — базовый URL вашего воркера
(`https://another-edge.<ваш-subdomain>.workers.dev`), а `$SPACE` — адрес Space
(`https://nargan-projects.hf.space/another`). Команды для PowerShell.

```powershell
$WORKER = "https://another-edge.ВАШ-SUBDOMAIN.workers.dev"
$SPACE  = "https://nargan-projects.hf.space/another"
```

### Шаг 0. Убедиться, что задеплоено актуальное

Раньше `/enroll` отдавал клиенту узлы с адресами-заглушками
(`cf-worker.another.example`) и без поля `control_plane`, без которого клиент
не может авторизоваться. Теперь воркер подставляет туда собственный адрес из
входящего запроса. Если воркер давно не переразвёртывался, сделайте это:

```powershell
cd another\edge
npx wrangler deploy
```

Проверка, что воркер жив:

```powershell
curl.exe -s "$WORKER/health"
# {"status":"ok","service":"another-edge"}
```

### Шаг 1. Стать администратором

Если вы уже проходили этот шаг по `DEPLOY.md` (`keygen` + `admin-register`) —
пропустите. Файл ключа администратора — единственный вход в панель;
потеряется, придётся заводить нового админа через CLI.

Откройте `$SPACE/admin/`, укажите файл ключа, введите passphrase и нажмите
**Unlock + bootstrap**. Ключ не покидает вкладку: подписи считаются в браузере.

Если сразу появляется `Cannot create a key using the specified key usages` —
это не неверный passphrase. Так браузер отказывается импортировать seed
Ed25519 как `raw`. На Space должен быть `app.js`, который оборачивает seed в
PKCS#8; после деплоя обновите вкладку через Ctrl+F5.

Пустые таблицы после входа — это нормально, устройств пока нет.

### Шаг 2. Создать приглашение себе

В панели, в блоке конфигурации, выполните операцию **invite**. Можно указать
комментарий и лимит трафика.

В ответ вы получите три значения:

- `client_id` — идентификатор устройства в базе;
- `enrollment_token` — **одноразовый**, живёт **24 часа**, показывается **один
  раз** (в базе лежит только его SHA-256, восстановить нельзя);
- `qr_payload` — та же информация в виде ссылки `another://enroll?token=...&cp=...`,
  нужна мобильному приложению; нам сейчас не понадобится.

Скопируйте токен сразу. Если потеряете — просто создайте новое приглашение.

### Шаг 3. Собрать клиент

Нужен Go 1.24 или новее. `wintun.dll` на этом шаге ещё не требуется.

```powershell
cd another\core
go build -trimpath -o another-core.exe .\cmd\desktop
```

Получится один самодостаточный exe примерно на 13 МБ, CGO не нужен.

### Шаг 4. Запустить ядро без прав администратора

Начинать стоит именно так: без TUN и без kill switch. Тогда ядро не трогает
сетевые настройки системы, не требует прав и работает как «библиотека
протоколов» — этого достаточно, чтобы проверить всю цепочку авторизации и
туннеля.

```powershell
$env:ANOTHER_ALLOW_NOOP_TUN = "1"
.\another-core.exe
```

В логе появится `local control API listening addr=127.0.0.1:47821` и
предупреждение `tun: using noop` — так и должно быть.

Строка `tun: using noop (трафик ОС не перехватывается)` означает ровно то, что
написано: системный трафик пока не заворачивается.

**Оставьте это окно открытым.** Дальнейшие команды — из второго окна
PowerShell.

### Шаг 5. Узнать публичный ключ устройства

Ключи генерируются при первом обращении и остаются на диске (по умолчанию
`.another/keystore`). Приватный ключ никуда не отправляется.

```powershell
$identity = curl.exe -s http://127.0.0.1:47821/identity | ConvertFrom-Json
$identity.public_key
```

Должно быть 64 hex-символа. Порядок здесь именно такой: ключ создаётся раньше,
чем устройство узнаёт свой серверный `client_id`.

### Шаг 6. Обменять приглашение на доступ

Это и есть enrollment. Go-ядро само его не выполняет — в норме это делает
Flutter, а мы сделаем вручную.

```powershell
$body = @{
  enrollment_token   = "ВСТАВЬТЕ_ТОКЕН_ИЗ_ШАГА_2"
  public_key         = $identity.public_key
  public_key_mldsa65 = $identity.public_key_mldsa65
} | ConvertTo-Json

$enroll = curl.exe -s -X POST "$WORKER/enroll" `
  -H "Content-Type: application/json" `
  -d $body | ConvertFrom-Json

$enroll | ConvertTo-Json -Depth 5
```

В ответе должно быть `ok: true`, ваш `client_id`, `vless_user_id` и список
`nodes`. Проверьте в `nodes`, что `host` — реальный адрес вашего воркера, а
`control_plane` заполнен. Если там осталось `another.example` — воркер
переразвёрнут не был, вернитесь к шагу 0.

Токен сгорел: повторный `/enroll` с ним даст `403`. Для нового устройства
нужно новое приглашение.

### Шаг 7. Смоук-тест: один туннель, без VPN

Проверяем всю цепочку — подпись, `/auth`, WebSocket, VLESS, выход в интернет —
не затрагивая систему. Непустой `dest_host` включает режим одиночного потока
вместо полного VPN (`connect_usecase.go:51-52`).

```powershell
$connect = @{
  client_id = $enroll.client_id
  nodes     = $enroll.nodes
  dest_host = "example.com"
  dest_port = 443
} | ConvertTo-Json -Depth 5

curl.exe -s -X POST http://127.0.0.1:47821/connect `
  -H "Content-Type: application/json" -d $connect

curl.exe -s http://127.0.0.1:47821/status
```

`{"ok":true}` и статус `connected` означают, что работает всё: воркер принял
подпись, выдал сессию, поднял туннель и открыл TCP до `example.com`.

Если `ok: false` — смотрите поле `error` и лог в первом окне: там видно, на
каком узле и на каком шаге сорвалось.

### Шаг 8. Полный VPN

Здесь уже нужны права администратора и драйвер TUN.

1. Скачайте `wintun.dll` с [wintun.net](https://www.wintun.net/) и положите
   рядом с `another-core.exe`. Разрядность — под вашу систему (`amd64`).
2. Закройте ядро из шага 4 и запустите новое окно PowerShell **от имени
   администратора**, уже без `ANOTHER_ALLOW_NOOP_TUN`:

```powershell
cd another\core
.\another-core.exe
```

Предупреждения `tun: using noop` быть не должно. Если оно есть — DLL не найдена
или не хватает прав; полного VPN в этом состоянии не будет.

3. Подключайтесь **без** `dest_host` — пустой адрес и означает «весь трафик»:

```powershell
$vpn = @{ client_id = $enroll.client_id; nodes = $enroll.nodes } | ConvertTo-Json -Depth 5
curl.exe -s -X POST http://127.0.0.1:47821/connect -H "Content-Type: application/json" -d $vpn
```

Ядро создаст интерфейс `Another` с адресом `10.7.0.2` и пропишет маршруты
`0.0.0.0/1` и `128.0.0.0/1` — так весь трафик уходит в туннель, при этом
исходная таблица маршрутов не затирается.

Проверка: откройте сайт, который показывает ваш IP. Он должен принадлежать
Cloudflare. Помните про ограничения из части 2 — QUIC и сайты за Cloudflare
могут вести себя не так, как ожидается.

Отключение:

```powershell
curl.exe -s -X POST http://127.0.0.1:47821/disconnect
```

### Шаг 9. Посмотреть на себя из админки

Вернитесь в `$SPACE/admin/`. После подключения там должны появиться
устройство, сессия и события. Трафик обновится не сразу — он записывается по
завершении соединения.

## Если что-то не выходит

| Симптом | Причина |
| --- | --- |
| `/enroll` → `403 invalid or already-used enrollment token` | Токен уже использован или истёк (24 часа). Создайте новое приглашение |
| `/enroll` → `403 enrollment token expired` | То же самое, но срок истёк явно |
| В `nodes` адрес `another.example` | Воркер работает на старой версии, сделайте `wrangler deploy` |
| `/connect` → `ok: false`, в логе `node auth failed` | Воркер не смог проверить подпись: устройство не привязано к базе, забанено или исчерпало квоту. Проверьте устройство в админке |
| `/connect` → `ok: false`, в логе `node dial failed` | Авторизация прошла, но туннель не поднялся. Обычно `host` в узле недостижим либо сессионный токен истёк, не дождавшись WebSocket |
| Всё зелёное, но сайты не открываются | Скорее всего DNS или ограничения из части 2. Сначала проверьте по IP, минуя имена |
| `tun: using noop` при запуске от администратора | Нет `wintun.dll` рядом с exe или не та разрядность |

Полезно знать: `session_token` живёт **120 секунд** и проверяется только в
момент открытия WebSocket. Само соединение потом живёт сколько угодно. Это
важно, если проходите `/auth` руками через `curl` — между `/auth` и
подключением нельзя долго думать. Ядро делает оба шага подряд, так что при
обычной работе ограничение незаметно.

## Что стоит сделать дальше

Ни один из пунктов не обязателен для работы, но каждый закрывает реальный
пробел.

- **UDP.** Сейчас всё, кроме DNS, ломается молча: клиент запрашивает UDP, а
  получает TCP. Честнее либо реализовать UDP в воркере, либо явно отклонять
  такие потоки с внятной ошибкой вместо подмены протокола.
- **Автоматический enrollment в ядре.** Токен уже умеет встраиваться в бинарник
  через ldflags, но `cmd/desktop` его для `/enroll` не использует — шаг 6
  приходится делать руками. Это же уберёт необходимость в Flutter для
  первого запуска.
- **Второй узел.** Failover реализован и работает, но переключаться некуда:
  живой узел ровно один. Второй появится вместе с data plane из
  `deploy/origin/` на Render или VPS.
- **Учёт трафика в реальном времени.** Пока сумма пишется в конце соединения,
  долгая сессия не видна в квоте. В архитектуре на это заложен счётчик на
  Durable Object.
- **Своё доменное имя.** `*.workers.dev` блокируется целиком и заметен. После
  переезда на собственный домен править конфиг не придётся: адрес узла
  выводится из входящего запроса.
