# ADR 0002: Собственная реализация VLESS вместо использования xray-core/sing-box

## Статус
Принято.

## Контекст
`xray-core` (лицензия MPL-2.0) и `sing-box` (лицензия GPL-3.0) — эталонные,
проверенные реализации протокола VLESS. Естественный вопрос — почему не
взять их напрямую как зависимость или не скопировать нужные файлы.

## Решение
Склонировали оба репозитория **только для чтения** (`/home/claude/reference/`,
не входит в проект) и вычленили точный wire-format запроса/ответа VLESS v0:

```
Запрос:  [1]version=0x00 [16]UUID [1]addons_len=0x00 [1]command [2]port_BE [1]addr_type [N]addr
Ответ:   [1]version [1]addons_len [N]addons(discard)
```

Затем реализовали кодирование/декодирование самостоятельно
(`core/internal/adapters/transport/vlessproto/`), без переноса кода
референсов.

## Обоснование
1. **Лицензии.** Копирование кода GPL-3.0 (`sing-box`) потребовало бы, чтобы
   зависимый код (потенциально весь `core/`) был совместим с GPL-3.0 — что
   ограничивает дальнейшее использование проекта. Переписанный по фактам
   протокола код такому ограничению не подлежит: сам by-byte формат
   сообщения — это факт совместимости протокола, а не объект авторского
   права.
2. **Объём.** Полноценное использование `xray-core`/`sing-box` как Go-модуля
   тянет за собой дерево зависимостей (gVisor, quic-go, utls, grpc,
   protobuf...), большая часть которого резолвится через домены вне нашего
   сетевого whitelist (см. ADR 0001). Сам протокол VLESS (без Reality/XTLS)
   — компактный и его достаточно реализовать под наши нужды.
3. **Архитектурное соответствие.** Самостоятельная реализация сразу ложится
   в наши интерфейсы (`ports.OutboundTransportPort`), без адаптации чужого
   API поверх него.

## Последствия
- VLESS-WS (Tier1) полностью рабочий и покрыт тестами.
- VLESS-Reality (Tier2) и VLESS-over-gRPC оставлены как заглушки — там
  дельта сложности между "переписать самим" и "взять зависимость" уже не в
  пользу первого варианта (см. комментарии в `vless_reality.go`, `vless_grpc.go`).
- При любых будущих правках протокола VLESS на стороне xray-core/sing-box
  (маловероятно — протокол стабилен) потребуется вручную сверить
  `vlessproto` заново.
