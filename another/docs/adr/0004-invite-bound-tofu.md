# ADR 0004: Invite-bound TOFU, не pre-provisioned ключ в бинарнике

## Статус
Принято (аудит 2026-08-25).

## Контекст
Оператор описал выдачу: сгенерировать пары, публичные в Mongo, приватные
зашить в per-client compile. Цель — пользоваться могли только те, кому
выдали приложение.

В коде v1 — TOFU: устройство само рожает Ed25519, одноразовый
`enrollment_token`. Приватный ключ устройство не покидает.

## Решение
Укрепляем TOFU, ключ в бинарник **не** кладём. В per-client build — token,
client_id, entrypoints. Сборка из админки — да. Сайт самообслуживания
(портал `/another/`, код инвайта → очередь GitHub Actions → скачать zip) —
**в скоупе**, см. [user-portal-plan.md](../user-portal-plan.md). Ключ по-прежнему
не в exe.

Полный разбор угроз: [provisioning.md](../provisioning.md).

## Почему не ключ в exe
Инсталлятор тогда равен учётке. `strings`/декомпилятор достаёт любой секрет
из файла независимо от Ed25519 vs ML-DSA. Шаринг файла = шаринг доступа.
Одноразовый token делает неактивированную копию бесполезной; активированный
keystore — отдельная компрометация, лечится revoke.

## Последствия
`KeyStorePort.LoadOrCreateDeviceIdentity()` без параметра client_id —
сохраняем (инвариант handoff §4.2). PQ добавит поля в identity, не индекс
по client_id.
