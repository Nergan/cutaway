# Спецификация аутентификации Another (v1)

> Отталкивается от внешнего черновика `research-en.md` (PQ-ETA v2.0), но **не
> является его реализацией**. Черновик смешивает несколько разных задач
> (подписи, replay, византийский консенсус, ZKP, PUF) в одну конструкцию,
> большая часть которой либо некорректна для нашей модели угроз, либо
> нереализуема на нашей инфраструктуре. Ниже — что из него берём, что
> выбрасываем и почему, и какая схема ставится на место.

Связанные решения: [ADR 0003](adr/0003-web-admin-pq-auth.md),
[ADR 0006](adr/0006-pq-hybrid-identity.md), [provisioning.md](provisioning.md).

---

## 0. Разбор `research-en.md`: что не так

Черновик ставит правильные **цели**: гибрид classical+PQ, не копить использованные
nonce в таблице до бесконечности, пережить обрыв связи, не хранить ключ в
`localStorage`, замечать аномалии. Решения под эти цели в черновике — нет.

### 0.1 Берём

| Идея черновика | Как используем |
|---|---|
| Гибрид Ed25519 + ML-DSA-65, успех только если **оба** валидны | Идентичность устройства и админа. `Sig = Sig_Ed25519 ‖ Sig_ML-DSA-65` |
| ML-KEM-768 | Не «сессия ради сессии». Внутреннее шифрование тел **админ-команд** на origin, чтобы Cloudflare Worker был слепой трубой (TLS терминируется на CF — без этого оператор CF читает бан/invite). Для клиентского `/auth` достаточно TLS; KEM там не обязателен в v1 |
| Порядковые nonce / hash-chain вместо множества used-nonce | У админа: монотонный `seq` + `chain_head` (O(1) состояние, нет GC). У клиента VPN: оставляем выдачу nonce Durable Object — частота `/auth` другая, seq на клиенте ломается при переустановке |
| Risk score по паттернам | Отдельный контур наблюдаемости, **не** часть verify() каждого пакета. См. [observability.md](observability.md) |

### 0.2 Выбрасываем (и почему)

**Рекурсивные ZKP (Halo 2 / Circle STARK).**
Доказывают вычислимое утверждение, не «этот запрос не replay». Верификатору
(нашему серверу) **нужно** видеть действия админа — это не zero-knowledge
сценарий. Halo 2 — Rust, нормального Python/TS-стека нет. Трудозатраты —
исследовательский проект на месяцы, к VPN и админке не относится.

**«Каждый узел шлёт всю историю, общая как блокчейн, fork-choice по сложности».**
Узлы — наши, не византийские. Источник истины уже есть: MongoDB. Глобальная
цепь на всех админов сериализует независимые действия (бан клиента A и бан
клиента B) и порождает ложные «форки» при гонке. Правильная модель: **цепь на
каждую идентичность** + атомарный `findAndModify` в Mongo. Это и есть «общая
история для всех узлов» без gossip и без майнинга.

**Bloom-фильтр как детектор replay.**
Вероятностный, ложные срабатывания. В черновике сами написано «это только
сигнал». При монотонном `seq` он не нужен.

**PUF + TEE + HSM как обязательный слой.**
На админской Windows-машине и на телефоне пользователя этого нет. Сделать
обязательным = админка не откроется. Опционально когда-нибудь (Android StrongBox,
Windows TPM) — не блокер.

**Key ratchet `K_{n+1} = KDF(K_n, salt)` без транскрипта.**
Без привязки к transcript рукопожатия это не forward secrecy, а смена байтов.
Настоящий FS уже даёт TLS 1.3 (и PQ KEM на CF). Свой ratchet имеет смысл только
внутри E2E-обёртки админ-команд (см. §3), с нормальным HKDF-extract по
`(kem_ss, seq, prev_hash)`.

**MAGIQ Framework, SGCP как «свой протокол из одной буквы».**
MAGIQ — про policy в multi-agent AI, к client/server verify не относится.
Свой протокол ниже назван прямо: **Another Auth v1**, без выдуманных акронимов.

**liboqs-python / PQClean как единственный стек.**
На Go-клиенте — библиотека с реализацией FIPS 204/203 (кандидат:
`github.com/cloudflare/circl` или эквивалент). На Worker — WebCrypto Ed25519
сейчас; ML-DSA в workerd ещё за флагом / PR, поэтому verify ML-DSA на origin
(Python) или WASM, пока натив не стабилен. Python: не liboqs-python вслепую,
а поддерживаемый биндинг (например `liboqs` / `pqcrypto` — выбрать на этапе
кода по тому, что ставится и не тянет native hell). Это деталь реализации,
не спецификации безопасности.

## 1. Модель угроз именно для аутентификации

Противник:

- сеть (replay, подмена тела, перестановка, повтор доставки, гонка двух путей);
- вор, который украл инсталлятор **до** enroll (не должен получить доступ);
- вор, который украл уже активированное хранилище ключей (криптографически
  неотличим от владельца — только детект аномалий + revoke);
- квантовый противник **в будущем** (harvest-now-decrypt-later на записанный
  TLS нам менее интересен, чем подделка идентичности — поэтому гибридная
  **подпись**, не только KEM);
- Cloudflare как терминатор TLS на входе (не считаем его «врагом VPN-трафика»,
  но **админские** команды — root: Worker не должен видеть plaintext).

Не противник: MongoDB Atlas и наши Docker-origin (HF/Render) — они и так
источник истины. Защита «от собственного хостинга» — вне скоупа, как в
архитектуре v2.0.

Приватный ключ админа **нельзя** класть в `localStorage`, cookies,
нешифрованный IndexedDB.

## 2. Идентичность

Каждый субъект (устройство VPN или админ) — гибридная пара:

```
Identity = {
  ed25519_pub,     # 32 байта
  mldsa65_pub,     # ML-DSA-65 (NIST level 3)
  # приватные только локально
}
```

Подпись сообщения `M`:

```
sig_ed   = Ed25519.Sign(sk_ed, M)
sig_pq   = ML-DSA-65.Sign(sk_pq, M)
sig      = sig_ed ‖ sig_pq
verify   = Ed25519.Verify AND ML-DSA.Verify   # оба обязательны
```

Каноническая сериализация `M` — length-prefixed поля, не JSON «как получится»
(иначе два узла подпишут разное). Точный layout — в коде рядом с тестами
golden-векторов, как уже сделано для VLESS.

Алгоритм только ML-DSA без Ed25519 **не** используем: длиннее, медленнее, меньше
платформенной поддержки. Гибрид — это hedge, не замена.

### 2.1 Где лежит приватный ключ

**Клиент VPN:** OS secure storage (DPAPI / Secret Service / Android Keystore).
Не файл в каталоге приложения в открытом виде в релизе (сейчас `file_keystore`
— dev-grade, для релиза заменить). Не бинарник. См. [provisioning.md](provisioning.md).

**Админ (Web):**

1. Ключ генерируется CLI `another-admin keygen` на машине оператора.
   Публичная часть вносится в Mongo (`admins[]`).
2. Приватная часть — файл, закрытый passphrase (или age). Раздаётся тем людям,
   кому оператор дал админку, **вне полосы** (не по тому же каналу, что Web).
3. Браузер **не хранит** ключ. На сессию: File System Access / выбор файла →
   расшифровка в RAM → подпись запросов из WASM → при закрытии вкладки память
   сбрасывается.
4. Усиление (не блокер v1): обернуть файловый ключ через WebAuthn **PRF**
   (ключ шифрования не извлекается в JS в открытом виде на диске без токена).

Это не login+email и не пароль. Это тот же класс, что SSH-ключ, только гибридный.

## 3. Админ-API: цепочка запросов без блокчейна

Состояние **на одну** админ-идентичность в Mongo (общее для всех origin —
HF, Render, будущий VPS):

```
admins.admin_id
  ed25519_pub, mldsa65_pub
  last_seq: uint64          # последний принятый
  chain_head: bytes32       # SHA3-256(...)
  last_body_hash: bytes32
  last_response: bytes      # идемпотентный повтор
  revoked: bool
  kem_pub: ML-KEM-768       # для E2E тел команд
```

Клиент админки после расшифровки ответа знает `last_seq` и `chain_head`
(хранит только в RAM на время сессии; при новом логине запрашивает
`GET /admin/session-bootstrap` — этот запрос сам подписан `seq=last+1` либо
использует одноразовый bootstrap-challenge, см. §3.2).

### 3.1 Обычный запрос

```
body          = канонический payload команды (invite/revoke/...)
body_hash     = SHA3-256(body)
M             = "another-admin-v1" ‖ seq ‖ chain_head_prev ‖ body_hash
sig           = HybridSign(M)

wire          = ML-KEM wrap(session_key) + AEAD(session_key, {seq, chain_head_prev, body, sig})
              когда путь идёт через CF Worker; на прямом TLS к origin можно
              упростить до TLS-only, но единообразие проще
```

Origin (не Worker) атомарно:

```
if revoked: REJECT
if seq == last_seq AND body_hash == last_body_hash:
    return last_response          # повтор после обрыва, не replay атаки
if seq != last_seq + 1: REJECT    # дыры и перестановки
if chain_head_prev != chain_head: REJECT
verify hybrid sig on M
execute body
new_head = SHA3-256(chain_head ‖ seq ‖ body_hash ‖ sig)
store last_seq, new_head, last_body_hash, response
return {new_head, result}
```

Атомарность: `findAndModify` / транзакция Mongo с предикатом
`last_seq == expected`. Два origin не примут два разных body на один seq.

Это закрывает:

- replay (seq уже использован с другим hash → reject; с тем же → cached);
- подмену тела (sig и body_hash);
- гонку двух узлов (атомарный seq);
- обрыв после execute до ответа (клиент шлёт то же seq+body, получает кэш).

Nonce-таблицу с TTL и cron-чисткой **не ведём**.

### 3.2 Первый запрос сессии (bootstrap)

Чтобы не хранить `chain_head` в браузере между сессиями, origin выдаёт
challenge (случайные 16 байт, TTL 60 с, Durable Object или тот же Mongo с
коротким TTL **на challenge**, не на все исторические nonce). Админ
подписывает `bootstrap ‖ challenge ‖ kem_ephemeral_pub`. После успеха
клиент получает `{last_seq, chain_head}` и дальше живёт по §3.1.

Challenge одноразовый. Это узкое место «выданных nonce», но их ровно столько,
сколько попыток входа, и TTL короткий. Не путать с историей команд.

### 3.3 Зачем не «общая история всех узлов как цепь блоков»

Действие админа A «забанить X» и админа B «выдать invite Y» коммутируют.
Глобальный блокчейн заставил бы одного ждать другого и объявлял бы fork при
параллели. Общий **аудит-лог** (append-only, capped) — да, это не цепь
аутентификации. Аутентичность лога: каждая запись содержит `admin_id, seq,
body_hash` уже принятого запроса. Подделать запись без ключа админа нельзя;
выбросить середину capped-коллекции при переполнении — **можно и нужно**
(затирание старых логов — требование оператора).

## 4. Клиент VPN (`/enroll`, `/nonce`, `/auth`)

Клиентский hot path другой: много устройств, частые короткие сессии,
переустановка приложения сбрасывает локальный seq.

**Enroll (invite-bound TOFU):**

```
POST /enroll {
  enrollment_token,
  ed25519_pub,
  mldsa65_pub
}
```

Token одноразовый, hash в Mongo. Привязываются **оба** публичных ключа.
Приватные на сервер не едут и в бинарнике не живут.

**Auth:** оставляем challenge-response:

```
GET  /nonce  → Durable Object выдаёт nonce (TTL 60с), строгая консистентность
POST /auth   { client_id, timestamp, nonce, sig_hybrid(nonce ‖ timestamp) }
```

Проверки как сейчас: окно времени, бан KV, consume nonce атомарно, verify
**обоих** алгоритмов, квота, session_token в KV.

Почему не seq-цепь как у админа: потерять локальный счётчик = вечная блокировка
до ручного reset. У админов единиц, у клиентов — переустановки. DO-nonce уже
решает replay между PoP (Cache API — нет).

Worker в v1 может проверить Ed25519 нативно (WebCrypto) и **проксировать**
проверку ML-DSA на origin (mongo-прокси / auth-helper на HF), пока ML-DSA в
workerd не включён стабильно. Оба должны пройти. Нельзя принять «только Ed25519
ок, PQ потом».

## 5. Что сознательно не делается в v1

- Аттестация железа / PUF.
- ZKP-сжатие истории.
- Общий блокчейн между узлами.
- Хранение невалидных nonce «на всякий случай».
- Пароль+email для админки.
- Post-quantum подпись как защита от декомпиляции инсталлятора.

## 6. Векторы и тесты (обязательны при реализации)

- Golden: одно и то же `M` → Go и Python/WASM дают верифицируемую пару подписей.
- Replay seq, replay nonce, fork (два body на один seq), retry того же body.
- Отзыв админа посередине сессии.
- Enroll вторым token-ом / вторым ключом на тот же сгоревший token — reject.
- Worker без origin PQ-verify не имеет права вернуть session_token.
