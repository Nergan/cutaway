# Наблюдаемость и админ-монитор

Админка — не «формы invite/revoke», а монитор системы плюс рычаги бана.
Стриминга (WS/SSE сквозь HF/Render/Vercel), на который можно опереться, **нет**.
Всё, что «почти realtime» — **поллинг**. Квота: порядка **1 минуты** (как
сейчас батч Durable Object) достаточно. Сессии, алерты, здоровье узлов —
чаще (5–15 с), это всё равно поллинг.

## Задачи монитора

1. Выдать / отозвать доступ (invite, revoke user, revoke client, переиздание).
2. Собрать инсталлятор для `client_id` (не сайт самообслуживания).
3. Понять, жива ли сетка узлов.
4. Увидеть активные сессии.
5. Заметить вредоносное: флуд, подбор `/auth`, перехват/повтор, отравление
   данных, попытка деанонима (коррелированные входы), шаринг профиля.
6. Читать компактные логи с затиранием хвоста.
7. Оповещения внутри админки (не Telegram, не email-как-обязаловка).

## Компактные логи и затирание

Эфемерный диск HF (до 50 ГБ) **нельзя** считать журналом: рестарт Space
стирает всё. GitHub/Cloudinary — не для логов.

**MongoDB capped collection** `events` (круговой буфер):

- фиксированный потолок (ориентир: десятки МБ, не сотни — M0 всего 512 МБ);
- документ = одно событие, плотное (без payload пользовательского трафика);
- старое затирается новым само (свойство capped);
- опционально gzip поля `extra` если без него не обойтись.

Категории событий (примеры): `auth_ok`, `auth_fail`, `enroll`, `ban`,
`quota_flush`, `ping_fail`, `anomaly`, `admin_cmd`. Без URL чужих сайтов
из туннеля (это не прокси-лог оператора спецслужб, это монитор своей сети).

Полные «как tcpdump» логи не храним. Если понадобится дебаг узла — кольцевой
файл **на время сессии** внутри контейнера, не в Atlas.

## Активные сессии

Показывать: `client_id`, узел входа, с какого entrypoint, байты за окно,
время старта, грубый регион/ASN по IP **если оператор явно включил** (по
умолчанию — минимально: hash IP, не сырой, спор с «деанонимом своих»).
Сырой IP в UI — отдельный флаг «режим расследования», не дефолт.

## Здоровье узлов и пингер

В админке список целей: `{name, url, interval_s, expect_status}`.
Пишется в Mongo, Worker Cron читает через REST-прокси (или KV-копию).
Добавить ping — форма, не новый деплой. HF, Render, будущий VPS, сам Worker
(`https://<worker>/health`) — все в одном списке.

## Детектор вредоносного (алерты)

Поллинг агрегатов, не ML на пакетах. Пороги — в админке, дефолты разумные.

| Сигнал | Зачем |
|---|---|
| Всплеск 4xx на `/auth` | подбор, украденный инсталлятор без ключа |
| Две живые сессии одного `client_id` с разных ASN | шаринг профиля / кража keystore |
| Enroll с IP, не похожим на «ожидаемый» (опционально) | перехват token |
| Резкий скачок `bytes_used` | раздача доступа, «арбуз» |
| Fork админ-цепи (`seq` занят другим body_hash) | атака на админку, см. auth-spec |
| Ping fail N раз подряд | узел лёг, пора смотреть failover |
| Рост `auth_fail` по одному `client_id` | ключ не тот / клиент сломан |

Алерт = запись в `events` + строка в колокольчике админки (acked/unacked).
Никакого Telegram. Если позже понадобится push — отдельный адаптер, не ядро.

«Отравление данных / деаноним / перехват» целиком криптографией не
вычисляются. Вычисляются следствия: рассинхрон chain_head, повтор nonce,
невозможные seq, два субъекта с одним ключом. Текст в UI — «аномалия типа X»,
не юридическая квалификация.

## Стек админки

- Web UI (вёрстки оператора — когда дойдём до UI, не первым шагом).
- Отдельный backend API (тот же процесс, что mongo-прокси, на HF; дубль образа
  на Render). PyMongo **Async**, не motor, не синхронный pymongo в async-цикле.
- Аутентификация — [auth-spec.md](auth-spec.md), не email/password.
- Telegram-бот в `control-plane-admin/another_admin/bot/` — **снят со скоупа
  релиза**. CLI Typer можно оставить как driving-адаптер для keygen/аварий.
