# Провижининг устройств

## Решение (коротко)

**Не зашиваем приватный ключ в инсталлятор.**

Оставляем (и укрепляем) модель **invite-bound TOFU**:

1. Оператор в админке создаёт приглашение → `client_id` + одноразовый
   `enrollment_token` (TTL, hash в Mongo).
2. По желанию админка **собирает** инсталлятор, в который зашиты только:
   token, URL входов, `client_id`. **Не** приватный ключ.
3. Первый запуск на устройстве: пара Ed25519 + ML-DSA-65 рождается в
   защищённом хранилище ОС, публичные ключи уходят на `/enroll` вместе с token.
4. Token сгорает. Копия того же инсталлятора больше не регистрируется.
5. Скомпрометировали устройство / человек раздал профиль — оператор жмёт
   revoke и выдаёт **новое приглашение** (переиздание) тому же человеку.

Это закрывает заявленную цель («пользуются только те, кому я дал доступ»)
лучше, чем pre-provisioned keypair в бинарнике. Обоснование — ниже и в
[ADR 0004](adr/0004-invite-bound-tofu.md).

Автосборка инсталлятора из админки — **в скоупе релиза** (кнопка «собрать для
этого client_id»; на ENROLLED-устройстве это reissue). Сайт самообслуживания
на HF Space: пользователь вводит одноразовый invite-код на `/another/` и
скачивает zip. Компиляция — GitHub Actions, не образ Space. Подробности —
[user-portal-plan.md](user-portal-plan.md).

## Почему не ключ в компиле

Угроза, которую хотелось закрыть постквантовой криптографией («скопировал
установщик, декомпилировал») — это **две разные угрозы**, и алгоритм подписи
не лечит ни одну из них сам по себе.

| Угроза | Что происходит | Что помогает | Что не помогает |
|---|---|---|---|
| Свой человек отдал инсталлятор чужому | Чужой ставит программу | Одноразовый token: второй enroll отклоняется. Если отдали уже активированный профиль (скопировали каталог ключей) — это кража идентичности, лечится **баном client_id** + алерт «два источника». | ML-DSA vs Ed25519 |
| Чужой снял `strings` / декомпилер с exe | Достаёт всё, что лежит в бинарнике | **Не класть секрет в бинарник.** Обфускация только повышает цену реверса протокола, не прячет ключ. | Стойкость подписи к квантовому компьютеру |
| DPI/регулятор хочет понять протокол | Смотрит handshake и паттерн | Reality / xHTTP / CDN-вход, смена транспортов. См. [circumvention.md](circumvention.md) | Ключ в бинарнике (ещё и помогает: один dump = чужой вход) |
| Один инсталлятор поставили десятерым | Квота и сессии скачут | Алерт «concurrent sessions / anomaly», бан, переиздание | Зашитый один ключ на всех — **ухудшает**: десятеро легитимны криптографически |

Если приватный ключ лежит в exe (ldflags, `go:embed`, «слабо обфусцированные
байты»), его достанет любой, у кого есть файл. Тогда инсталлятор **и есть**
учётная запись. Раздать копию = раздать доступ. TOFU с одноразовым token
делает ровно наоборот: файл установщика без живого приглашения — пустышка.

Совпадение «этот билд ↔ этот человек» даёт token, а не ключевая пара. Пара
привязывается к **устройству** после первого запуска.

## Что именно зашивается в per-client build

```
embedded:
  client_id: "drug-iz-pitera-a1b2"
  enrollment_token: "<одноразовый>"
  entrypoints: ["https://cf-worker…", "https://hf-space…", …]
  build_id: "<уникальный, для учёта артефакта>"
не embedded:
  private_ed25519
  private_ml_dsa
```

После успешного `/enroll` клиент забывает token (или помечает израсходованным).
Повторный запуск той же установки идёт в `/auth` со своими ключами.

## Переиздание

В админке, не в клиенте (пароля у пользователя нет):

1. `revoke` старого `client_id` (бан + инвалидация KV).
2. Новое приглашение на того же `user_id` (комментарий «телефон заменили»).
3. Сборка нового инсталлятора / выдача нового token.
4. Старый бинарник без нового token бесполезен; старый ключ в бане.

Если когда-нибудь появится локальный секрет «пароль приложения» — сменить его
может только уже аутентифицированная сессия ядра. Сейчас такого пароля нет и
не требуется: секрет — ключ устройства в OS store.

## Что остаётся слабым (честно)

- Пользователь может скопировать **уже активированное** хранилище ключей на
  вторую машину. Криптографически это то же устройство. Детект: две активные
  сессии, разные IP/ASN, всплеск квоты → алерт оператору. Идеально не закрывается
  без hardware-binding (TEE/аттестация), которого на Win7/типичном Android нет.
- Реверс протокола по бинарнику возможен всегда. Снижаем: нейтральное имя,
  минимум говорящих строк, per-build token (не секрет, но ломает универсальный
  «вот вам готовый конфиг»), разнообразие транспортов.
- Первый, кто успел ввести украденный ещё не использованный token, занимает
  слот. Смягчение: короткий TTL, алерт «enroll с неожиданного IP», кнопка
  «сбросить неактивированное приглашение».

## Отношение к будущему сайту автовыдачи

Сайт на HF Space с одноразовым ключом скачивания — отдельный контур, не
админка. Админка оператора остаётся местом, где создаётся этот ключ и
смотрите логи сборок. Не проектируем сайт в этом релизе, но API приглашений
делаем таким, чтобы сайт потом стал ещё одним клиентом того же backend.
