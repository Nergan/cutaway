# Оркестратор проектов

Корневой hub публикует приложения из явного реестра `orchestrator.toml`.
Каталоги больше не сканируются автоматически: новый проект не запустится, пока
не будет добавлен в manifest.

## Режимы

- `CUTAWAY_PROFILE=local|hf|render` выбирает профиль хостинга.
- `CUTAWAY_ISOLATION=isolated` запускает каждый проект отдельным дочерним
  uvicorn-процессом. Hub проксирует HTTP и WebSocket, но не импортирует плагины.
- `CUTAWAY_ISOLATION=embedded` монтирует объявленные роутеры в процесс hub.
  Этот режим предназначен для локальной разработки и не защищает hub от OOM,
  зависания event loop или падения native-библиотеки проекта.
- Значение `auto` включает процессы на POSIX и embedded-режим на Windows.

Docker-образ Hugging Face использует профиль `hf` и изоляцию процессов.

## Политики проекта

Каждая запись `[projects.<id>]` определяет каталог, entrypoint, URL-префикс,
зависимости, разрешённые переменные окружения и политику исходящей сети. Блок
`limits` задаёт:

- частоту, размер и общий минутный объём HTTP-трафика;
- конкурентность, очередь и таймаут запросов;
- число и размер WebSocket-сессий;
- RAM, CPU, число процессов, соединений и размер временных файлов;
- бюджет рестартов, backoff и idle timeout.

Supervisor суммирует ресурсы всего дерева процесса. При превышении лимита он
останавливает только нарушивший worker, открывает circuit breaker и оставляет
hub и остальные проекты доступными. CPU нельзя аппаратно throttling-овать без
cgroups: при длительном превышении процесс останавливается.

Все worker внутри одного Space работают под одним Unix-пользователем. Это
изоляция сбоев и случайных записей, но не security sandbox для намеренно
вредоносного кода. Для такого кода требуются отдельные контейнеры/аккаунты.

Исходящие HTTP-запросы, использующие `shared_network`, дополнительно получают
allowlist доменов, проверку redirect и DNS, запрет private/link-local адресов и
лимит запросов. Произвольный native-код может обойти Python-политику; для
абсолютной сетевой изоляции нужен firewall или отдельный контейнер хостинга.

## Глобальное отключение

Файл `<project>/.project-ignore` является fail-closed kill switch:

```toml
run = true
build = true
deploy = true
reason = "Why the project is disabled."
```

Он не отключает CI. Проект `another` использует этот механизм. В HF-профиле
также отключён `yellow_mirror`, поскольку remote-browser функциональность
несовместима с политикой публичного Space.

## Сборка и деплой

В isolated-профилях `build.sh` создаёт отдельный venv для hub и каждого
активного проекта в `.orchestrator/venvs/<profile>/`. Версии зависимостей одного
проекта больше не перезаписывают зависимости соседнего.

`scripts/prepare_deploy.py --profile hf` удаляет из временного CI checkout
проекты с `deploy = false`. Без `--dry-run` скрипт отказывается работать вне CI,
если явно не передан `--force`.

Автоматический deploy `another` отключён. Его CI остаётся активным, а edge и
installer workflows можно запустить только вручную. Уже развёрнутый Cloudflare
Worker этот репозиторий автоматически не удаляет.

## Добавление проекта

1. Добавить каталог и entrypoint, экспортирующий `router` или `asgi_app`.
2. Добавить `[projects.<id>]`, `limits`, `network` и только необходимые имена
   секретов в `env_allowlist`.
3. Добавить профильные overrides для тяжёлых или запрещённых функций.
4. Выполнить:

   ```bash
   python -m orchestrator.config --profile local validate
   python -m orchestrator.config --profile hf validate
   pytest -q tests
   ```

## Диагностика

- `GET /healthz` показывает состояние hub, профиль, режим и доступность MongoDB.
- `GET /api/status` показывает состояние worker, число рестартов, текущие
  ресурсы и время до закрытия circuit breaker.
- Worker стартует лениво при первом запросе и останавливается после idle timeout.
